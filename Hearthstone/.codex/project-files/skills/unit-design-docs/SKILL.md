# 单位设计文档

为 `AutoDoc/Design/` 下的敌机和我方舰船玩家视角设计文档建立一物一档规则。本 skill 不适用于 `AutoDoc/DesignPlan/` 策划案。

## 确定覆盖范围

1. 先根据当前项目事实或主代理明确提供的已核验范围，列出本次涉及的敌机与我方舰船。
2. 用户要求编写、补齐或重整全项目单位设计文档时，覆盖当前已实现的全部敌机和我方舰船。
3. 用户明确限定单位或模块时，只覆盖该范围；但范围内每一种单位都必须有独立文档，不得抽样或合并。
4. 不凭策划案、未来计划或名称猜测补写尚未实现的单位。无法确认某单位是否存在时，标记待核验，不写成当前事实。

## 判定“一种单位”

- 玩家能以独立名称、外形、行为、武装或耐久规则识别的敌机或我方舰船，视为一种单位。
- 同一单位的阶段、可破坏部件和纯外观受损状态写在同一篇文档中。
- 能独立出现、受击或结束的召唤单位按独立敌机记录。
- 只有外观差异、玩法规则完全相同的皮肤不另建单位文档；在所属单位文档中说明外观变体。

## 一物一档

- 每一种敌机只保留一篇单位设计文档，推荐路径为 `AutoDoc/Design/Units/enemy-aircraft/<unit-id>/<unit-id>.md`。
- 每一种我方舰船只保留一篇单位设计文档，推荐路径为 `AutoDoc/Design/Units/player-ships/<unit-id>/<unit-id>.md`。
- `<unit-id>` 使用稳定的英文小写 kebab-case；标题与正文可以使用中文展示名。
- 敌机总览、舰船选择或战斗系统文档可以保留共享流程，但不能替代单位文档。总览只概括并链接单位文档，不重复维护整套单位细节。
- 遇到把多种单位合写在一起的旧文档时，在本次覆盖范围内把单位专属内容迁入独立文档；共享内容留在总览，避免两处事实源。

## 选择格式

- 编写或更新敌机单位文档时，必须读取并遵循 [敌机单位文档格式](references/enemy-aircraft-format.md)，不要读取舰船格式。
- 编写或更新我方舰船单位文档时，必须读取并遵循 [我方舰船单位文档格式](references/player-ship-format.md)，不要读取敌机格式。
- 同时处理两类单位时，分别读取两份格式，并对各自文档独立套用；禁止混合章节结构。

## 通用写作规则

1. 只记录当前已实现、可由项目确认且玩家可感知的体验；使用现在时。
2. 描述玩家看到的外观、入口、操作、反馈、行为、数值和功能边界，不写代码类名、API、调用链、序列化字段或内部架构。
3. 数值会显著影响识别、决策或结果时写出当前值；不要把“可配置项”或未来调参空间当成当前规则。
4. 共享系统只写该单位如何使用或偏离共享规则，并链接对应总览；不要在每篇单位文档中复制完整公共机制。
5. 创建或重命名目录与文件时使用英文；正文使用用户的语言。
6. 图片遵循项目设计文档媒体规则，只展示当前体验。敌机和我方舰船的图片都直接放入各自“外观与动画”章，不建立独立“参考图”章；没有有效图片时不放占位图。

## 完成检查

1. 对照本次单位清单，确认每一种单位恰有一篇文档，且没有同一单位的重复事实源。
2. 确认敌机文档只用敌机格式、舰船文档只用舰船格式，章节顺序与省略规则正确。
3. 确认单位展示名、身份、关键数值、玩家交互和结束边界与当前项目一致。
4. 检查总览与单位文档的链接、相对图片路径和英文文件路径均可访问。
5. 删除空章节、占位语、未来预期、内部实现细节和已迁移后的重复描述。
