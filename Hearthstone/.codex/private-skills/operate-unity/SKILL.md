# 操作 Unity

处理需要 Unity Editor 的资产生成、物件构建、场景操作与测试。先发现当前环境真实可用的 Unity MCP，再按任务类型选择执行通道；只有必须由 Unity Editor 序列化或导入的资产生成脚本强制通过 Unity MCP 执行，其他操作不把 MCP 当作完成前提。

## 1. 确认项目边界

1. 先读取项目根目录 `AGENTS.md`、主代理规则和当前任务命中的专项 skill。
2. 复用项目已有公开 Editor API、构建入口、资产生成器和测试入口，不另建平行流程。
3. 保护用户正在使用的 Editor、未保存 Scene、Prefab 与 Asset；未经许可不关闭、重启或强制终止 Editor。
4. 不手写 Scene、Prefab、Material、ScriptableObject 或其他 `.asset` 序列化 YAML；不手动创建、编辑或删除 `.meta` 文件。

## 2. 从完整工具集发现 Unity MCP

每次需要 Unity Editor 能力时先执行一次发现，不把提示中顶层展示的工具列表当作完整目录：

1. 检查当前直接工具、延迟工具目录以及环境提供的工具搜索能力。
2. 若环境提供 `tool_search`，搜索 `Unity`、`Unity MCP`、`unityMCP` 与所需能力；若提供代码执行器内的 `ALL_TOOLS`，搜索名称或描述中的 `unity`，重点识别 `mcp__unityMCP__` 前缀，但不得把该前缀硬编码为唯一实现。
3. 找到候选工具后读取本次所需工具的实际 schema。优先识别实例资源、Editor 状态、控制台读取、C# 代码执行、菜单执行、资产管理和测试工具。
4. 若存在实例资源，先确认目标项目实例；多个实例并存时使用工具提供的实例选择能力固定到准确实例。
5. 用无副作用的 Editor 状态或活动场景查询确认工具可调用。顶层没有展示工具，不能单独作为 MCP 不可用的证据。

完整目录仍没有 Unity MCP，或发现的工具无法端到端调用时，只记录当前会话不可用。除非用户当次明确要求使用、诊断或恢复 Unity MCP，否则不要安装、改配置、重启 Editor 或进入恢复流程；用户明确要求时读取并遵循 `$recover-unity-mcp`。

## 3. 按任务选择执行通道

### 3.1 生成 Unity 资产

最终文件必须通过 `AssetDatabase`、`PrefabUtility`、`ScriptableObject`、Importer、Scene 保存或其他 Unity Editor 序列化/导入能力生成时，必须通过已发现且可调用的 Unity MCP 执行生成脚本：

1. 优先调用现有公开资产生成入口。已有菜单项时可使用 MCP 的菜单执行工具；可直接执行 C# 时，优先使用 MCP 的内存代码执行工具，例如语义等同于 `execute_code` 的能力。
2. 生成逻辑较长或需要复用现有类型时，可在项目允许的位置编写最小 Editor C# 脚本，等待 Unity 编译成功，再通过 Unity MCP 调用其公开入口。脚本文件的创建不等于资产已经生成。
3. 执行前确认目标路径、覆盖策略和输入来源；不得静默覆盖用户已有资产。代码执行工具提供安全检查时保持启用，不通过反射或外部进程规避限制。
4. 通过 Unity API 保存并刷新资产数据库，再从 Editor 重新加载目标资产，核对类型、路径、关键序列化字段和依赖引用。
5. 读取编译与执行后的 Console 错误；工具调用成功但资产未落盘、无法加载或出现新增错误时，不得判定完成。

普通 C# 源码、JSON、CSV、图片原文件等不需要 Unity Editor 序列化即可生成的文件，不属于本节强制 MCP 范围；它们仍按各自专项 skill 和项目规则处理。

### 3.2 构建物件与场景内容

GameObject、组件、Prefab 内容、Scene 层级、UI 物件或测试场景的构建不强制使用 MCP。根据当前环境选择下列任一项目允许的通道：

- Unity MCP 的物件、Prefab、Scene 或 UI 工具；
- 调用项目已有公开 Editor 构建入口；
- 临时 Editor C# 脚本、Unity 命令行 `-executeMethod` 或其他可审计的脚本通道。

脚本必须使用 Unity 公共 API 让 Editor 完成序列化，不得直接改写 YAML。临时脚本应具有唯一触发条件和幂等保护，确认执行完成后删除脚本源码；`.meta` 交给 Unity 管理，不手动处理。

### 3.3 测试与验证

测试、Play Mode 启动、构建验证、日志检查和静态检查不强制使用 MCP。优先使用项目已有测试入口、StageGroup 入口、Unity Test Framework、Unity 批处理或仓库脚本；MCP 测试工具只是可选通道。

不要因为 Unity MCP 不可用而阻塞本可通过脚本完成的物件构建、测试或一般 Editor 操作。使用批处理前确认不会与用户正在运行的同一项目 Editor 冲突，并保留退出码、测试结果和日志证据。

## 4. 脚本与执行要求

1. 先编写或定位脚本，再等待 Unity 完成导入与编译；有编译错误时不得继续使用新增类型或执行生成入口。
2. 脚本只承担当前任务所需的 Editor 调用，复用项目公开 API，不复制生命周期、资源管理、Stage 或测试框架。
3. 让可重试操作保持幂等：执行前检查现有资产或物件，明确创建、更新或拒绝覆盖，不因域重载重复执行。
4. 临时入口使用唯一名称或 `SessionState` 键，避免污染正式菜单与运行时代码；完成后移除临时源码并重新确认项目可编译。
5. 不使用私有 Editor Bridge Socket、临时 Python/PowerShell MCP 客户端、桌面 UI 自动化或其他旁路来伪装 Unity MCP 调用。

## 5. 验收与汇报

至少记录并核对：

- 搜索的是顶层工具还是完整工具目录、发现了哪些 Unity MCP 能力、最终选择了哪个实例与工具。
- 资产生成脚本是否确实由 Unity MCP 执行，以及返回值、Console、落盘路径、重新加载和关键字段验证结果。
- 物件构建或测试使用的非 MCP 通道、执行命令或入口、退出码及产物。
- 临时脚本是否清理、是否产生新增编译错误、是否误改无关 Scene、Prefab、Asset、Build Settings 或用户 Editor 状态。

若 Unity MCP 不可用，继续完成允许使用脚本的其他范围；仅把“必须由 MCP 执行的资产生成脚本”标记为未完成，并准确报告已准备的脚本、确认的断点和所需下一步，不得声称资产已生成。
