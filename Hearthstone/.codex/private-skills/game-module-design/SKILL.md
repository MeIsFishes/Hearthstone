# 游戏模块设计（以数据为中心）

当用户要求设计游戏模块时，在开始阶段把本 skill 的必要检查项加入项目根目录 `AutoDoc/Temp/` 下的任务检查清单。清单用于结束审计，不要求执行过程中逐项标记，也不限制调研和设计的实际顺序；任务结束前逐项复核并写独立报告。即使处于 Plan 模式，也允许创建和完成这些审计文件。

---

## 0. BbxCommon 总体设计基线

先按下表确定职责，不为同一份信息建立平行状态：

| 职责 | 默认承载位置 |
|---|---|
| 随 Entity、关卡或会话变化的运行时状态 | `EcsRawComponent` / `EcsSingletonRawComponent` |
| 策划配置、静态表格和资源描述 | `DataApi` + `BbxScriptableObject` / `CsvDataBase` |
| 持续或按帧执行的游戏规则 | `EcsMixSystemBase` |
| Stage 存活期间的事件响应 | `StageListenerBase` |
| UI 表现、交互和数据监听 | `UiViewBase` + `UiControllerBase`，Model 仍来自 ECS Component |
| Timeline、行为树、演出等托管逻辑 | Task；结果与长期状态仍回写 ECS 或业务数据 |
| System、UI、数据组、场景和加载项的作用域 | `GameStage` 组合 |
| 文本、Sprite、Mod 等资源读取 | `ResourceApi`；规则见 `bbxcommon-resource` |

设计时遵循以下原则：

- **先数据、后逻辑**：先确定数据的唯一权威来源，再决定谁产生、谁消费；System、Controller、StageListener 和 Task 通过同一份数据协作。
- **组合而非复制**：复用已有 Component、Data、Stage 和 Task 节点；不要为了某个 UI 或临时流程复制一套状态。
- **使用公开入口**：业务层优先使用 `EcsApi`、`DataApi`、`UiApi`、`TaskApi`、`ResourceApi` 及公开扩展方法，不直接依赖底层 Manager 和存储结构。
- **底层变化留在模块内**：性能优化、缓存、加载策略和语法糖尽量在对应 BbxCommon 模块内部完成，避免把同一优化散落到多个业务模块。
- **按数据域划分职责**：一个模块应围绕一组相关数据及其生产、消费和 UI 展开，而不是仅按“逻辑代码”“界面代码”横向切开。

进入实现时沿用 BbxCommon 命名约定：public/internal 成员与类型使用大驼峰；protected/private 字段使用 `m_` + 大驼峰；枚举以 `E`、接口以 `I` 开头；缩写按一个单词处理，避免 `Idx`、`Mgr` 等跳字母缩写。存在 `Create/BbxCommon/Script` 模板时优先使用模板，再按业务命名调整。

## 1. 明确需求与功能点确认

在开始数据与架构设计之前，先完成**需求层面的对齐**。

### 1.1 明确需求（歧义与追问）

通读用户描述，尽力识别**可能产生歧义或落地风险**之处，例如：

- 目标与边界（做什么、不做什么；与现有玩法/界面的关系）。
- 术语与规则是否与项目惯例一致（若用户用词与代码里已有概念可能不是同一回事，需对齐）。
- 触发条件、频率、失败/成功/取消等行为是否说清。

对**仍不明确**的条目，**向用户询问确认**，得到可执行的表述后再进入后续步骤；不要凭猜测带过。

### 1.2 功能点清单与用户确认

在需求表述已对齐的前提下，**分点列出**本模块需要实现的**功能点**（每条尽量独立、可验收，例如用有序列表或分项 bullet）。

将这份功能点清单**提交给用户确认**：是否完整、是否有遗漏、是否有误解。用户确认或修订后，再以修订后的功能点作为 §2 及之后步骤的输入。

## 2. 列出新增数据，不确定处向用户确认

先根据 **§1 已确认的功能点与需求** 列出本模块涉及的**全部状态与规则**，并标出每一项：

- **含义**（例如：当前关卡剩余时间、角色水平输入、移动速度上限）。
- **谁产生、谁消费**（仅自己模块 / 与其它系统交界）。
- **是否已存在**：能否复用现有 **`DataApi`** 条目或已有 **`EcsRawComponent`**，避免重复造字段。

对以下情况**必须向用户追问**，直到可落地：

- 规则边界不清（胜负条件、是否唯一玩家、是否跨关卡保留）。
- 数据归属不明（全局一份还是每实体一份；是否进存档）。
- 与现有系统冲突或命名重叠。

产出物：一张「数据清单」草稿（可用表格），作为后续步骤的输入。

## 3. 静态配置 vs 动态运行时

对清单中每一项归类，按下面规则判断（**若不确定某条数据是否应做成可配置，向用户询问**）：

- **游戏固有的配置项**（策划在局外调整、不随单局过程当作「状态」变化）：用 **CSV**（**`CsvDataBase`**）或 **`BbxScriptableObject`**，加载后登记到 **`DataApi`**。
- **游戏中会变化的属性**，或**从属于某个游戏对象 / 会话**的运行时数据：用 **`EcsRawComponent`**（挂在 **Entity** 上）；全场唯一一份的用 **`EcsSingletonRawComponent`**。
- **既要局外可调配置，又要在运行时按实体/会话持有变化**：**同时**需要配置侧（**DataApi**）与 **Component** 两侧各建一类。

CSV 与 BbxScriptableObject 的选型、**DataGroup** 与 Stage 的对应关系，实现时见 **`config-data-design`**。

## 4. 谁访问数据：UI vs 业务逻辑

### 4.1 需要新的界面或 HUD

参考文档 **`bbxcommon-ui`**。

- 明确该功能有几个普通页面、Hud 和动态条目；不能明确时向用户询问。
- 为每个页面创建唯一一对 Controller 和 View，列出 View Prefab 的静态层级与序列化组件引用。静态页面不得设计为由 Controller 运行时拼装；动态重复条目使用独立条目 Prefab/View/Controller 与已有 UiList/对象池能力。
- 明确每个页面所属的 UiScene、UiGroup、默认显隐和 GameStage。加入现有 UiScene 时必须修改对应 UI 编辑场景并重新导出；新增 UiScene 时必须规划 UiGroup 枚举/类、UI 编辑场景、`UiSceneExporter`、Prefab 实例、导出 Asset、GameEngine 引用和 GameStage 注册的完整步骤。
- Hud 按 `HudViewBase` / `HudControllerBase`、Entity Bind/Unbind 与 ModelWrapper 监听流程设计，不把 Hud 当普通全屏页面注册。
- 方案中找不到 UI 编辑场景却出现 `UiSceneAsset`，或 Controller 负责创建整页静态结构时，判定为框架外设计并继续修订，不得进入最终 plan。

**Model**：不单独建一套 Model 类型；**Controller** 通过 **监听 ECS 上的 Component** 更新 **View**。

### 4.2 业务逻辑（非 UI）

先问：**这段逻辑是否需要每帧执行，或在一段时间内持续执行？**

- **是**（每帧、固定步长、或持续多帧的模拟/扫描）→ 新增 **`EcsMixSystemBase`** 派生类，在 **`GameStage`** 上 **`AddUpdateSystem` / `AddFixedUpdateSystem`**，并 **`[DisableAutoCreation]`**（见 **`bbxcommon-ecs`**，子文档 `new-class-examples/mix-system.md`）。需要稳定相对顺序时，把类型加入 GameEngine 的 **`RegisterSystemOrder(typeof(...), ...)`** 列表；未登记 System 默认追加在已登记项末尾，不依赖 Stage 注册顺序或 DOTS 顺序 Attribute。

- **否**——不是「持续 tick」，而是**在特定条件下响应事件**（例如变量变脏、可监听项的回调、与 Stage 存活期绑定的订阅）→ 优先考虑 **`StageListenerBase`** 子类，在 **`AddStageListener<T>()`** 中注册；在 **`InitListener`** 里挂接 **`Listenable`** / **`ListenableVariable`**，在 **`OnUnload`** 统一拆除。

若逻辑本质是「进入 Stage 时做一次、离开时清理」，放在 **`IStageLoad`**（**`AddLoadItem` / `AddLateLoadItem`**）往往更合适；**StageListener** 更偏向**存活期间的事件订阅**。若单次行为很复杂，也可结合 **Task** 等（按项目惯例），本 skill 不展开。

## 5. 检查美术资产是否齐备

### 5.1 先评估已有美术资产是否应当复用

设计新模块的美术表现前，先检查项目目前已有的 **UI 通用资产、背景底图、边框、面板、装饰、图标、遮罩和其他可能共用的 2D 图片**，逐项判断能否直接复用，不要默认每个新模块都需要重新制作一套同类资产。

检查来源至少包括：

- `AutoDoc/Art/UI/ui-art-overview.md` 中现有 UI 风格分组、通用资产和主要界面；新模块包含 UI 时，先判断应沿用哪个 `UI-STYLE-*` 分组。
- `AutoDoc/Art/Modules/` 下现有模块美术文档中的背景、装饰、图标和已有资产列表。
- `Assets/` 下实际存在的图片文件；文档记录只能作为检索入口，最终仍需确认真实文件和路径。

对每个候选资产按以下条件作出确定结论：

- **用途与语义**：资产表达的功能、主题和信息层级是否与新模块一致，是否会因跨模块复用造成含义混淆。
- **风格**：是否符合新模块采用的 UI 风格分组及项目整体的形状、线条、色彩、纹理和装饰语言。
- **规格**：尺寸、比例、分辨率、透明背景、九宫格边界、状态与视觉变体是否覆盖新用途。
- **修改影响**：直接复用是否无需改动原文件；若修改会影响已有使用方，应新增明确的变体资产，不得覆盖原资产后让其他模块被动变化。

满足用途、风格和规格时，方案默认引用同一份已有资产。仅需运行时着色、九宫格拉伸、裁切或已有规格允许的组合变化时，仍视为直接复用。确实不满足时，结论写为“已有但需要新增变体”或“无法复用，需要新增”，并说明原因；不得仅因为已有相似图片就强行复用。

### 5.2 检查资产完整性

根据已确认的功能点、游戏内表现和 UI 设计，列出模块实际需要的美术资产或资产组，并检查项目当前是否已经具备可直接使用的资产。至少逐项确认：

- 资产用途及出现位置，例如页面背景、按钮状态、图标、角色、场景物件、特效序列或其他视觉元素。
- 项目内是否存在对应资产；存在时记录实际路径，不得只凭命名或需求描述推断已经具备。
- 已有资产是否满足当前用途、风格、状态数量、尺寸和格式要求。
- 结论属于“已有且可直接复用”“已有但需要修改”还是“缺失，需要新增”。

检查时结合 `Assets/` 下的实际资源与 `AutoDoc/Art/` 下已有的美术规格；文档中的资产清单不能替代对项目内文件的确认。若无法从现有文件确定某项资产能否复用，向用户确认后再定。

对缺失或需要修改的资产，在方案中明确资产名或资产组、用途、规格要求、预期路径和处理方式，并纳入实现顺序与 Todo。不要把占位图或尚未创建的 Editor 资产写成已具备。若本模块确认没有任何美术表现或资产变化，可按 `plan-output-format` 的跳过规则省略美术章节。

产出物：一张「美术资产完整性检查」表，作为最终 plan 美术部分的输入。每项至少记录资产需求、候选已有资产及实际路径、复用结论、判断依据和后续处理；没有合适候选资产时也要明确写出“无”。直接复用项不得再列入新增资产清单；需要新增变体的项按新增美术资产处理，并保留与原资产的关系说明。

## 6. 设计 GameStage 归属

在已明确本模块会引入哪些 **System / StageListener / UiScene·UI / `IStageLoad` / DataGroup** 等之后，按以下决策树确定落点。**每一步若不能自行确认，向用户询问后再定。**

### 6.1 决策树

1. **查看 `GameEngine` 中现有的 GameStage 及其组合**（即各场景/模式下 `SetActiveGameStage` 的调用情况），判断本模块的逻辑**是否与某个已有 Stage 的职责一致**：
   - **是** → 直接把本模块的新增项并入该 GameStage（在同一 Stage 上继续 `Add…`）。
   - **否** → 进入步骤 2。

2. 判断本模块是否可以用**现有 GameStage 搭建新的组合**（即在某些场景下新增或去掉某几个已有 Stage 的组合，而不需要新建 Stage）：
   - **是** → 调整 `SetActiveGameStage` 的调用，使用现有 Stage 的新组合承载本模块。
   - **否** → 进入步骤 3。

3. **新建 GameStage**，并在 `GameEngine` 中规划该 Stage 参与哪些 `SetActiveGameStage` 组合（即在哪些场景/模式下它应当活跃）。

### 6.2 逐条对应

决策完成后，把本模块**每一项**待挂载内容逐条对应到**具名的 GameStage**（并入已有 / 新建），避免遗漏：

- 列出：**System**、**StageListener**、**UiScene / 页面 UI**、**`IStageLoad`**、**`AddScene`**、**`AddDataGroup`** 等（按实际用到项）。
- 对每一条写明所属 GameStage 名称。
- UiScene 除写明所属 Stage 外，还必须能对应到 `bbxcommon-ui` 规划的 UI 编辑场景与导出 Asset；Stage 注册不能替代 UiScene 的配置源和导出步骤。

若同一模块跨多个 Stage，此处应能一眼看出某个 Stage 不活跃时会带走哪些逻辑与 UI。

具体可向 Stage 挂载哪些项、**`LoadItem` 与 `LateLoadItem`** 等见 **`game-stage`**。

## 7. 抽出通用函数和新增枚举

项目中存在命名为 `*Utils` 的静态函数。在本次功能添加逻辑中，如果有通用逻辑满足以下条件的，可以放置到已有Utils类中。已有Utils类不合适的，可以新建Utils类：

1. 多处调用或未来可能在多处调用；
2. 需访问多个数据源（不同Component或者配置项。

**如果该函数只有一次调用，且未来大概率不会有其他调用，则不要写进Utils** 。

新增枚举项写进现有类中（一般写入Component类，UI相关的枚举一般写入UiController、HudController类）。
