# 设计阶段

本阶段只解决“这组 Task 图应该怎么配”的设计问题。

本阶段只产出设计方案和缺失节点/Context 的需求规格，不直接实现新增或修改节点、Context、Condition、Duration。

请将以下条目加入当前任务检查清单，供结束审计逐项复核；不以清单限制设计顺序：

1. 判断当前 Task 涉及的业务范围。
2. 了解现有哪些节点。
3. 拆分 Task 图集。

对于每一个 Task 图集，再将以下条目作为对应图集的子检查项加入清单：

1. 了解现有哪些类似图集和可复用子图。
2. 判断图的拆分方式。
3. 判断使用 Timeline 或行为树。
4. 读取主代理传入的 Context 并设计节点和字段。
5. 记录缺失节点规格。
6. 迭代到方案稳定。

# 需要了解的设计知识

`Task图集`、`Task图`、`Task节点` 的定义以 `bbxcommon-task` skill 的模块概览为准：先按业务范围拆 Task 图集，再拆可单独运行的 Task 图，最后设计每张图中的 Task 节点。

Task 图目前提供 Timeline 和行为树 2 种范式，Task 节点可任意应用于以上 2 种范式。

Task 节点的字段来源有 3 种：

1. 直接赋值；
2. Context 赋值，Context 本身是从游戏运行时传入的上下文；
3. Blackboard 赋值，寄存的动态变量，Task 可主动写入。

Blackboard 同时是 Task 用于实现节点间值传递的工具，例如可以设计一个节点 `AddAndWrite` ，逻辑是将 A 和 B 的值求和，然后写入一个给定的 Blackboard key 里， 在下一个节点中通过 key 读值。

另外， `RunTask` 这个节点会直接应用当前 Context 开启子 Task ，用于 Task 图集之间的通信。

Timeline 中的节点，当开始时间相同时，会严格遵守从上至下的顺序执行，也是节点间传值的保障。

# 步骤详解

## 1. 判断当前 Task 业务范围

判断当前要求设计的 Task 涉及或属于哪些系统，对于需要用到的节点做好预期。

## 2. 了解现有哪些节点

阅读 `AutoDoc/Task/TaskNode/TaskNodeIndex.md`，了解当前有哪些相关节点。索引只用于初筛；一旦准备使用某个节点，必须在 `AutoDoc/Task/TaskNode/` 目录下阅读对应单节点文档，确认字段名、字段类型、字段语义和逻辑可空性。

## 3. 拆分 Task 图集

明确本次需求需要哪些 Task 图集。如某一个完整的技能、某一个完整的关卡触发，都是一个单独的 Task 图集。

## 4. 了解现有哪些类似图集和可复用子图

阅读 `AutoDoc/Task/TaskGraph/TaskGraphIndex.md`，查找是否有类似的 Task 图集，了解设计思路。

如果需要仿照已有 Task 图的字段级设计，先读对应 `AutoDoc/Task/TaskGraph/` 模块文档找到 Task key 和配置路径，再按 `task-json-config-design` 中“如何阅读 `.task.setting`”的规则读取同 key 中间文件。若目标图没有 `.task.setting`，先按 `task-json-config-design` 的修改现有 Task 流程用转换脚本从 `.json` 反向生成，再阅读生成的中间文件。

阅读 `AutoDoc/Task/TaskContext/ReusableTaskGraphIndex.md`，查找是否有应该复用的子图。

## 5. 判断图的拆分方式

如果一个图集的逻辑过于复杂，可以考虑拆分子图。

例如对于火球术来说，如果每个等级的效果不完全一样，则可以将效果做成子图，然后入口图根据等级不同，传入不同的参数，实现不同等级的效果。

但注意不要滥用子图，如果一段逻辑并不复杂，且未来大概率不会复用，则不必拆分子图。

## 6. 判断 Timeline 或行为树

理论上行为树可以配出所有表现，而 Timeline 配不出复杂的逻辑和分支，但有些很简单的逻辑仍可选用 Timeline 。

适合 Timeline 的情况：

- 逻辑简单。
- 重点是按时间点触发表现或结算。
- 节点之间主要靠开始时间和持续时间组织。

适合行为树的情况：

- 逻辑复杂。
- 重点是顺序、选择、并行、循环或条件分支。

同一组设计里可以同时使用两者：入口图用行为树做分支，某个表现子图用 Timeline 控制时序。

## 7. 读取主代理传入的 Context 并设计节点和字段

读取主代理为当前 Task 图集传入的 TaskContext ，并为每个图设计节点和字段。若主代理没有传入 BindingContext，只记录为“缺少主代理输入”，不要在本阶段追问用户或自行猜测。

读取 `AutoDoc/Task/TaskContext/TaskContextIndex.md` 和对应单 Context 文档，确认主代理传入的 Context 中有哪些可用字段、字段含义和逻辑可空性。

优先复用已有节点。缺少节点时，先判断是否能通过合理抽象扩展现有节点解决；只有复用会造成错误语义、字段过度膨胀或逻辑无法表达时，才新增节点。

设计字段时，通过 Task 节点的文档确认每个字段的具体含义，以及哪些字段是必填的。

如对 Context 的字段含义和来源有疑义，读 `AutoDoc/Task/TaskContext/` 下对应文档。

使用 Blackboard key 时，必须在设计方案中写清该 key 的写入来源：来自前置节点写入、CSV/业务入口写入、或当前图新增写入节点。无法确认写入来源时，把该 key 视为缺失项，不要直接进入配置。

## 8. 记录缺失节点规格

具体设计过程中，如果发现有 Task 节点缺失，只记录缺失节点规格，交给主代理实现。

缺失节点规格至少写明：

- 节点名。
- 归属：底层 Task 或业务层 Task。
- 节点类型建议：TaskNode、TaskOnce、TaskDuration 或 TaskCondition。
- 用途。
- 字段需求：字段名、字段类型、字段来源和逻辑可空性。

如果是完全不依赖业务语境的通用节点，归为底层 Task；如果依赖具体玩法、技能、AI、关卡或业务数据，归为业务层 Task。

## 9. 迭代到方案稳定

把“已有节点是否够用、是否需要新增节点、图要拆几张、每张图用什么类型、字段从哪里来”反复对齐。若记录了缺失节点，回头重新检查这些节点规格是否能满足配置、是否需要继续迭代。

本阶段结束时，应能明确每张图的 Task key、图类型、绑定 Context、节点列表、节点关系和字段赋值。

须将新增的 Task 图集和节点列表汇报给用户。
