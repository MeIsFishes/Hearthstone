# 增量初始化

## 目录

1. 目标
2. 现有占位结构盘点
3. 冲突处理
4. 可重复执行
5. 迁移边界

## 1. 目标

近空项目通常已经有一部分目录或占位类。初始化的目标是让这些内容形成可运行链路，而不是用标准模板覆盖它们。

## 2. 现有占位结构盘点

对每个候选文件记录：

| 项目 | 问题 |
|---|---|
| 路径/namespace | 是否符合现有业务根目录和程序集？ |
| 职责 | 是真实职责、模板占位还是重复入口？ |
| 消费者 | 谁创建、注册或调用它？ |
| 生命周期 | 何时创建、何时释放？ |
| 依赖 | 引用了哪个框架版本和程序集？ |
| 验证 | 能否编译、是否进入启动链？ |

优先把孤立的现有类型接入正确链路；只有确定它纯属无用模板时，才向用户说明并请求删除或在明确授权范围内删除。

## 3. 冲突处理

### 已有 GameEngine

不要创建第二个。检查它是否继承当前 `GameEngineBase<T>`、是否被场景挂载、是否在 `OnAwake()` 调用至少一个具名 GameStage Group 入口，并由该入口通过 `SetActiveGameStage(...)` 激活完整集合。近空项目只有零散 `LoadStage` 时，在不改变已有业务语义的前提下补成初始 Group 入口；已经形成项目采用旧模型时不借初始化流程强制迁移。

### 已有多个 Stage 方案

辨别哪些是常驻 Stage、模式 Stage 和已废弃占位。不要用 Stage 添加顺序或 DOTS 顺序 Attribute 表达 System 执行顺序；在现有 GameEngine 的 `RegisterSystemOrder(typeof(...), ...)` 类型列表中统一登记。不要把 `LoadStage` 和 `SetActiveGameStage` 混成两套长期状态模型。优先使用现有项目已经采用且框架文档支持的组合方式。

### 已有 Component 但没有 System

确认 Component 是运行时权威数据，然后创建真实消费者 System；若它其实是静态配置，迁移决策必须先与用户确认，不要静默改类型。

### 已有 System 但没有注册

检查 `[DisableAutoCreation]`，将其注册进职责对应的 Stage，并按依赖加入 GameEngine 的 `RegisterSystemOrder` 类型列表，补齐数据创建和卸载。不要移除特性来依赖 DOTS 自动创建；确实不要求相对顺序时可不登记，该 System 会在已登记项之后运行。

### 已有 UIModel

阅读消费者。如果它已经承载真实项目状态，不在初始化时强制迁移；记录其与当前 ECS Model 惯例的差异。若只是空模板，不继续扩建，新的页面优先监听 ECS Component。

### 已有 asmdef

修复引用而不是创建同名第二份。创建新 asmdef 会改变脚本所属程序集，必须检查 internals、Editor API、测试引用和循环依赖。

## 4. 可重复执行

初始化每一步都应可重复检查：

1. 路径存在则检查内容，不重复创建；
2. 类型存在则补职责，不生成同义类型；
3. Stage 已注册 System 则不重复 Add；
4. DataGroup 已添加则核对组名，不重复添加；
5. UiScene 已创建则复用，不创建第二场景根；
6. 用户尚未完成的编辑器步骤保持待办，不伪造资产；
7. 再次运行扫描脚本时，信号应从缺失/占位向已接通变化。

整套占位模板脚本会在写入前检查全部目标：已有相同内容时跳过，已有不同内容时停止且不写任何文件。近空项目发生冲突时，不使用覆盖选项；读取现有文件后手动补齐缺失职责。

## 5. 迁移边界

以下动作超出普通初始化，应先获得明确方向：

- 移动或重命名已有业务根目录；
- 改根 namespace；
- 把 Assembly-CSharp 全量迁入 asmdef；
- 替换已有 MVC/DI/事件体系；
- 导入或升级 BbxCommon、Entities、UniTask 等核心依赖；
- 删除模板、示例 Scene 或已有资源；
- 变更启动 Scene 和 Build Settings 中已有顺序。

如果不做迁移也能形成正确的最小可运行流程，先增量接通，再把迁移作为独立任务。
