## 1. 判定目标

本判定回答两个问题：

1. 当前是否适合执行“整体基础初始化”；
2. 如果适合，应从哪一层开始补齐，而不是重建全部内容。

“空”描述的是业务架构成熟度，不等于磁盘上没有文件。Unity 自动生成文件、BbxCommon、插件、示例资源、空目录、占位脚本和刚生成的 asmdef 都不能单独证明项目已经建立。

## 2. 证据来源

按优先级收集：

1. 用户明确描述的项目阶段与目标；
2. `AutoDoc/ProjectOverview.md` 或同类项目说明；
3. `ProjectSettings/ProjectVersion.txt` 与 `Packages/manifest.json`；
4. `Assets/Scripts/` 中排除 BbxCommon、第三方库、生成代码后的业务脚本；
5. 业务 asmdef、根 namespace 与程序集引用；
6. `GameEngineBase<T>` 子类、Stage 创建与激活代码；
7. ECS Component/System/实体创建与释放链路；
8. UiScene、View/Controller、Prefab 与 Model 监听链路；
9. Scene、Resources、配置资产和测试；
10. 可用时的 Unity 编译或 PlayMode 结果。

文件计数只能作为信号，最终必须阅读关键文件。一个有 500 个框架文件但没有业务代码的项目仍可能是空项目；一个只有 10 个脚本但能跑通完整业务流程的项目可能已经不是空项目。

## 3. 排除项

统计业务成熟度时排除或单独记录：

- `Assets/Scripts/BbxCommon/` 及其第三方依赖；
- `Assets/Plugins/`、`Packages/`、SDK 和商店资源；
- Unity/TMP 默认示例；
- 自动生成文件和导出数据；
- 只有注释、TODO、空生命周期函数的占位类；
- 从模板复制但没有被启动链路引用的样例代码；
- `.meta`、贴图、字体等不能证明业务链路的资产。

不要删除这些内容；这里只是避免误判。

## 4. 基础能力矩阵

逐项标为 `缺失`、`占位`、`已接通` 或 `不需要`：

| 能力 | 缺失 | 占位 | 已接通 |
|---|---|---|---|
| 项目身份 | 无业务 namespace/根目录 | 有名称但混用或未引用 | namespace、目录、程序集一致 |
| 编译边界 | 依赖不明或编译失败 | asmdef 存在但引用未验证 | 框架和业务程序集可编译 |
| 启动入口 | 无 GameEngine | 空子类或未挂场景 | 场景中的唯一入口开始加载 |
| Stage | 无 Stage | 只 Create、未激活或无内容 | Stage 可加载、卸载且职责明确 |
| 数据 | 无方案 | 目录/空类型存在 | DataGroup、类型、资产和读取一致 |
| ECS | 无 Component/System | 只有孤立模板 | 创建—运行—销毁完整 |
| MVC/UI | 无结构 | 只有 View 或 Controller | View/Controller、Model、UiScene 接通 |
| 首个业务流程 | 无 | 日志/样例未接启动 | 从入口到可观察结果完整 |
| 验证 | 无 | 只有人工口头说明 | 编译/运行/检查清单有结果 |

对于明确不需要 UI 的无头模拟或工具项目，将 MVC/UI 标为 `不需要`，不能因此判空。

## 5. 状态分类

### A. 非 Unity 项目

缺少 `Assets/`、`Packages/manifest.json`、`ProjectSettings/ProjectVersion.txt` 等 Unity 根标记。停止本 skill，不创建 Unity 结构。

### B. 完全空白 Unity 项目

只有 Unity 默认结构、包和少量默认资产；没有业务根 namespace、入口和真实脚本。执行完整初始化。

### C. 只有框架的空项目

已有 BbxCommon、插件或公共框架，但业务代码为零或只有样例。仍是空项目。保留框架，先确认依赖版本，再建立业务层。

### D. 只有占位结构的近空项目

已生成业务目录、asmdef、GameEngine/Stage 占位类或零散模板，但以下任一情况成立：

- 没有可从启动入口追踪的完整业务流程；
- ECS 只有 Component 或 System 的一端，未被 Stage 注册；
- MVC 只有目录或单边类型，未连接 ECS Model/UiScene；
- 绝大多数基础能力仍为 `缺失/占位`；
- 用户明确说明这是刚初始化的骨架，代码检查也未发现真实功能。

仍按空项目处理，但必须执行增量补齐，不能整体覆盖。

### E. 已形成项目

至少存在一个真实业务流程，并且可从入口追踪到生命周期容器和可观察结果；例如战斗 Stage 创建实体、运行多个 System、加载配置并驱动 UI。即使某个模块（如存档、UI 或测试）缺失，也不是空项目。

停止整体初始化。把缺口作为专项架构任务处理。

### F. 不确定

证据冲突，例如：代码看似完整但没有启动场景；大量脚本可能只是模板；用户称空项目但已有真实功能。先列出冲突证据，询问会影响目录/架构的最小问题。

## 6. 决策规则

按顺序应用：

1. Unity 根标记不成立 → A。
2. 无业务脚本且无 BbxCommon → B。
3. 无业务脚本但有 BbxCommon → C。
4. 有业务脚本但无真实业务流程，或入口/Stage/ECS/MVC 多数仍是占位 → D。
5. 有真实业务流程 → E。
6. 无法确认脚本是模板还是真实功能 → F。

真实业务流程至少应回答：谁启动、在哪个 Stage 生效、数据在哪里创建、逻辑在哪里运行、何时释放、结果如何观察。只有 `Debug.Log` 且未进入正式启动流程的临时测试不算真实业务流程。

不要用固定脚本数量作为硬阈值。数量可帮助发现异常，但不能取代语义判断。

## 7. 典型案例

### 案例 1：刚创建 Unity + 导入 BbxCommon

有数百个框架脚本，没有项目 namespace 和 GameEngine 子类。分类 C，执行完整业务层初始化。

### 案例 2：有 `FooGameEngine.cs`、空 `BaseStage.cs` 和目录树

入口没有加载 Stage，ECS/MVC 目录为空。分类 D，保留命名和文件，补齐启动流程和最小可运行流程。

### 案例 3：已有战斗 Stage 和 ECS，但没有主菜单 UI

战斗能创建实体、System 执行、退出时释放。分类 E。主菜单 UI 是后续模块，不执行空项目整体初始化。

### 案例 4：服务器仿真项目没有 UI

入口、Stage、ECS 和测试完整，需求明确不需要 UI。分类 E；MVC 标为不需要。
