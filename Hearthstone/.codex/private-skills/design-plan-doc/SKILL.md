# 策划案文档

`AutoDoc/DesignPlan/YYYY.MM.DD/` 保存游戏的设计意图与策划决策，允许包含尚未实现的目标、规则、数值假设、开放问题和取舍。它不是当前项目现状的事实源，也不是一次开发任务的实现计划。`AutoDoc/DesignPlan/Plan/` 和 `AutoDoc/DesignPlan/Review/` 分别保存策划案实现流程产生的实施 Plan 与最终实现审查意见，不属于策划案正文。

## 默认阅读边界

正常情况下，`AutoDoc/DesignPlan/` 下的文档通常没有参考价值。执行项目现状理解、问题诊断、方案设计、功能实现、验收或现状文档同步时，不要默认枚举、搜索或读取该目录。

只在以下情况读取其中直接相关的文档：

1. 用户明确要求创建、修改、评审、整理、比较或总结策划案。
2. 用户明确指定某篇策划案作为需求输入，或要求实现该策划案。
3. 用户要求追溯设计决策、方案演变或被取代原因，并且当前状态文档无法回答。

即使读取，也要先检查文档状态，只把它作为设计意图或指定需求，不把其中内容当作已经实现的功能。其他实现或验收任务需要判断当前项目状态时，由对应任务按自己的流程另行核验；不要在策划案正文中混入核验过程或实现结论。

## 编写资料边界

创建、维护或评审策划案时，除用户输入和目标策划案本身外，可以读取 `AutoDoc/Design/` 下直接相关的玩家视角设计文档、`AutoDoc/Art/` 下直接相关的美术文档、这些文档直接引用的现有图片，以及目标策划案直接引用的 `AutoDoc/DesignPlan/media/` 图片。不要无差别读取媒体或美术资源目录，也不要读取游戏代码、配置、`AutoDoc/Program/` 或 `AutoDoc/Temp/Plan/`，不要为了确认技术可行性主动调查实现。

如果用户提供的策划目标与现有玩家视角设计文档不同，把差异作为策划目标表达，不通过阅读代码裁决。只有用户明确要求额外参考某份非代码材料时，才读取其指定内容；代码实现始终不属于策划案写作依据。

## 文档职责

策划案回答“准备把游戏设计成什么、为什么这样设计”，保存玩法目标、玩家体验、规则、配置需求与视觉意图。可以提出玩法、UI、美术、音频或叙事需求。除用户明确要求写入第七章“实现方式建议”外，不得写成代码、类名、API、数据结构、生命周期、资源导出步骤或其他实现设计。

## 文档粒度与需求拆分

每篇策划案原则上只覆盖一个能够独立说明的功能点，或者同一模块内强关联、必须共同解释的功能点集合。不要按用户一次消息的边界机械建文档，也不要把一次提出的全部需求盲目塞进同一篇策划案。

写作前先分析用户的真实需求、玩家目标、对应场景、模块归属、规则依赖、配置关联和可独立验收程度，再提出文档数量与边界意见：

1. 不同模块、不同玩家目标、不同游戏场景，或可以独立设计和验收的功能点，默认拆成不同策划案。
2. 只有属于同一模块、服务同一玩家目标或连续场景、规则与配置强耦合，并且能由同一组原型图连贯表达时，才合并到一篇。
3. 用户的多条表述可能共同描述一个真实功能点；不要只按句子或编号机械拆分。
4. 更新既有策划案时，先判断新增需求是否仍处于原文档边界；不属于时创建新的策划案，不在旧文档中追加无关章节内容。
5. 按 `project-state-preflight` 的策划案分支，把真实需求分块、建议篇数、每篇范围和拆分/合并理由先写入任务检查清单，再开始正式写作。

## 路径与组织

1. 策划案按首次创建日期归档，路径固定为 `AutoDoc/DesignPlan/YYYY.MM.DD/<document-name>.md`。`YYYY` 是四位年份，`MM` 和 `DD` 分别是两位月份与日期，各段之间使用英文句点，例如 `AutoDoc/DesignPlan/2026.08.10/keyboard-weapon-rework.md`。
2. `<document-name>.md` 必须使用能表达策划主题的英文小写 kebab-case，不使用中文、空格、下划线或无意义编号。
3. 文件直接放在对应年月日目录下，不再按主题建立文档子目录。修改既有策划案时保留首次创建日期和原路径；只有用户明确要求迁移时才移动到其他日期目录。
4. 同一主题出现重大改版时，使用新的英文文件名保存新策划案；不要在同一正文中保留多套同时有效、无法判定优先级的规则。
5. 不为目录完整性主动创建空日期目录或空策划案；用户做到哪里，维护到哪里。

## 严格文件头

`In Design`、`Todo` 与 `In Progress` 策划案的文件开头三行必须严格使用以下格式：

```text
title: <策划案标题>
state: <状态>
priority: <优先级>
```

`Completed` 与 `Warning` 策划案由 `project-state-preflight` 的实现流程在步骤 g 写成五行文件头。`Completed` 使用：

```text
title: <策划案标题>
state: Completed
priority: <优先级>
plan: AutoDoc/DesignPlan/Plan/<document-name>-plan.md
review: AutoDoc/DesignPlan/Review/<document-name>-review.md
```

`Warning` 使用：

```text
title: <策划案标题>
state: Warning
priority: <优先级>
plan: AutoDoc/DesignPlan/Plan/<document-name>-plan.md
review: AutoDoc/DesignPlan/Review/<document-name>-review.md
```

第一行必须从文件第一个字节开始，不得在前面放置 UTF-8 BOM、空行、Markdown 标题、注释或 YAML 分隔符。所有字段名后的冒号后各保留一个半角空格；标题不能为空，可以使用用户的语言。`In Design`、`Todo` 与 `In Progress` 在第三行之后空一行，`Completed` 与 `Warning` 在第五行之后空一行，再开始正文。不要增加其他文件头字段、状态表或一级标题。`plan:` 与 `review:` 必须写项目根目录相对路径的纯文本，不得写 Markdown 链接，例如 `plan: AutoDoc/DesignPlan/Plan/example-plan.md`、`review: AutoDoc/DesignPlan/Review/example-review.md`；它们分别指向本篇最终实施 Plan 和最终实现审查意见，只允许出现在 `Completed` 或 `Warning` 文件头中。历史 `Completed` 文档缺少这两行时可以继续读取，但下次重新实施或重新完成时必须补齐。

`state` 只允许以下五个区分大小写和空格的精确值：

- `In Design`：策划仍在设计、讨论或修订中。
- `Todo`：策划内容已经确定，等待实现。
- `In Progress`：策划案已经进入实现流程，正在制定实施 Plan 或执行后续实现、审查与验收步骤，尚未达到 `Completed` 门槛。
- `Warning`：首次验收不通过后已经完成两趟“修改、代码复审、重新验收”，主干美术资产或主干程序功能仍未通过；正式 Review 必须记录失败证据与影响。
- `Completed`：策划案的主干美术资产、主干程序功能及使核心链路可用的关键回归已经完成落地并通过验收；少数非主干边界项验收困难或未通过时，已在正式 Review 的“待决策技术项”中如实记录。

`priority` 只允许以下三个区分大小写的精确值：

- `P0`：最高优先级。
- `P1`：中等优先级。
- `P2`：最低优先级。

优先级表达策划案之间的相对实施紧迫度，不代表状态或完成度。新建策划案必须填写优先级；用户已经指定时按用户结论填写。用户未指定时，主代理根据玩家价值、前置依赖、受影响范围和验证紧迫度提出暂定优先级及理由，在文档处于 `In Design` 时写入，并在本轮定稿确认中一并请用户确认。不得为了完成文件头而无说明地默认某个优先级。

新建策划案时必须使用 `state: In Design`，不得在第一次写作时直接创建为 `Todo`、`In Progress`、`Warning` 或 `Completed`。每次写作任务对既有策划案的正文、图片或其他文档内容进行修改时，也要先把状态改为 `In Design`，并移除 `Warning`、`Completed` 专用的 `plan:`、`review:` 行；只有根据用户定稿结论修改状态行本身时，不把该状态变更视为新一轮内容修改。

每轮创建或实质修改完成后，必须把本轮文档清单及各自优先级展示给用户并逐篇确认是否定稿。只有用户看过本轮结果并明确确认某篇已经定稿，才把该文档第二行改为 `state: Todo`；该确认同时确认第三行优先级。用户在写作前预先指定 Todo 不代替这次完成后的确认。用户未确认、明确不定稿或要求继续修改时保持 `In Design`，完成下一轮修改后再次确认。策划案写作流程不得把文档改为 `In Progress`、`Warning` 或 `Completed`；三者只由策划案实现流程分别在开始制定实施 Plan、首次验收失败且两趟验收修正后主干仍失败、主干验收通过时设置。

## 章节格式

严格文件头之后空一行，再依次书写以下六个必选二级章节，并按条件决定是否追加第七章：`In Design`、`Todo` 与 `In Progress` 的正文从第三行后开始，`Warning` 与 `Completed` 的正文从第五行后开始。前六章的名称、编号和顺序固定，不得省略、合并或重命名；除符合条件的第七章外，不得增加其他同级章节。第六章固定包含三个三级小节，其他章节需要细分时也只能在对应章节内增加三级标题。

### 1. 需求简述

使用 `## 1. 需求简述`。简要说明要解决的玩家问题、期望体验、设计目标和范围边界，让读者不依赖实现背景也能理解为什么需要该玩法。

### 2. 对应游戏场景

使用 `## 2. 对应游戏场景`。说明玩法位于玩家旅程的哪个阶段或界面、如何进入、在什么条件下发生、与前后流程如何衔接，以及在对应场景中玩家能够观察和操作什么。

### 3. 玩法原型图

使用 `## 3. 玩法原型图`。必须嵌入至少一张实际图片。可以直接采用能够准确表达玩法的现有图，也可以调用画图或图像编辑能力从零制作，或基于现有图修改；不要求每篇策划案都从零生成新图。Mermaid、ASCII、纯文本流程图、外部链接、空白框或“待补图”等占位内容均不计入完成。

如果整篇策划案仅描述程序侧需求或配置侧需求，则不需要配图；只要包含玩家可见的玩法、界面、场景、交互或状态表现需求，仍须遵循本节的配图要求。

原型图必须直接解释玩法，可表现玩家视角界面、场景布局、交互位置、关键状态或操作前后变化，不使用与玩法无关的装饰性概念图。一张图无法清楚覆盖多个界面、阶段或关键状态时，按需要增加图片。使用或修改现有图前先实际查看图片，确认内容与策划案匹配；需要修改时基于原图使用图像编辑能力，不覆盖原始游戏资产、文档图片或临时证据文件。

将最终采用的图片复制或输出到 `AutoDoc/DesignPlan/media/YYYY.MM.DD/<document-name>/` 下，其中年月日与策划案归档目录一致，`<document-name>` 与策划案文件名主体一致；图片文件名使用英文小写 kebab-case，并在 Markdown 中使用从策划案文档到图片的相对路径嵌入。每张图下方写一句图注，说明它表达的玩法状态或交互重点。

所有策划案流程产生并需要保留的图片都必须位于 `AutoDoc/DesignPlan/media/`，不得把 `AutoDoc/Temp/`、`AutoDoc/media/`、`Assets/`、项目外路径或 `AutoDoc/DesignPlan/` 下除 `media/` 外的目录作为正式图片存放位置。策划案正文原型图沿用上述目录；实现验收与最终 Review 使用的游戏内截图统一放到 `AutoDoc/DesignPlan/media/YYYY.MM.DD/<document-name>/review/`。日志、文本结果和录屏等非图片临时证据仍按实现流程放在 `AutoDoc/Temp/`。

对于需要配图的策划案，没有可用现有图且画图或编辑能力不可用、生成失败时，不得把策划案的 `state` 设置为 `Completed`，也不得把策划案写作任务报告为完成；保留该章节并明确报告阻塞。

### 4. 玩法详细设计

使用 `## 4. 玩法详细设计`。完整说明玩家目标、操作流程、规则、状态变化、反馈、成功与失败条件、限制和边界情况。可以使用流程、表格、公式与数值，但全部从玩法和玩家体验角度表达，不讨论如何编码或接入项目。可判定的验收方式和标准统一写入第六章，不在本章重复维护另一套验收清单。

### 5. 所需配置项

使用 `## 5. 所需配置项`。列出策划需要调整的语义参数，推荐使用“配置项、策划含义、建议值或范围、玩家可见影响”四列。配置项使用策划可理解的名称，只描述设计用途、单位、默认建议、上下限、相互约束和调节结果；不得设计代码字段、字段类型、配置类、表结构、序列化方式、资源键或存储路径。没有可靠数值时标记“待确认”，不要为了填表虚构数值。

### 6. 验收

使用 `## 6. 验收`，并严格按顺序包含以下三个三级小节；不得把三类内容合成一张无分类清单。

#### 6.1 验收方式

使用 `### 6.1 验收方式`。验收方式只使用以下三种名称；一篇策划案可以按验收点需要选择一种或多种，用户没有明确指定时默认使用“流程log验收”：

- **流程log验收**：进入对应游戏场景，按实际玩家流程操作，并用能够对应操作步骤和预期结果的流程日志作为主要证据。
- **游戏内截图**：进入对应游戏场景，操作到需要检视的玩家可见状态，并用游戏内截图作为主要证据。
- **仅功能验收**：不进入游戏场景，直接调用实际功能入口或使用最小范围的一次性轻量脚本，以可判定输出作为主要证据。

本节列出本篇采用的验收方式、各方式覆盖的 `ART-`/`FUNC-` 编号或范围、对应游戏场景与核心操作。选择多种方式时分别说明覆盖边界，不得用一种方式的证据替代其无法证明的验收点。不得在本节设计测试框架、代码结构或长期测试设施。

#### 6.2 美术资产验收

使用 `### 6.2 美术资产验收`。本节只验证策划案所需美术资产是否齐备，以及内容、构图、尺寸比例、色彩、辨识度、状态覆盖、风格一致性和玩家可见品质是否满足设计目标。推荐使用“编号、美术资产或资产组、前置场景、检视方式、预期玩家可见表现、通过条件”六列表格，编号使用稳定的 `ART-01`、`ART-02` 格式。

第 6.1 节未选择游戏内截图时，每个 `ART-` 项的检视方式必须写为检查相关资产编排，并列明需要确认的资产或资产组、引用与组合关系、层级/布局/状态编排和状态覆盖；选择游戏内截图时，写明需要进入的场景、操作到的状态和截图重点。

每项必须能够独立判断通过或失败；不得使用“资产正常”“表现正确”等模糊条件。不得写资源导出、文件路径、资源键、接入步骤、程序触发逻辑、代码、类名、API、数据结构或内部日志。策划案确实不涉及美术资产时，本节明确写“本策划案不涉及美术资产验收”并说明范围依据，不创建占位编号。

#### 6.3 程序功能验收

使用 `### 6.3 程序功能验收`。本节只验证玩家操作、玩法规则、状态变化、反馈时序、成功与失败条件、限制、边界情况以及配置变化带来的玩家可见结果。推荐使用“编号、前置场景、玩家操作、预期结果、通过条件”五列表格，编号使用稳定的 `FUNC-01`、`FUNC-02` 格式。

每项必须能够独立判断通过或失败，并覆盖主要玩法流程、关键状态变化、重要边界条件、失败或限制反馈，以及配置变化会直接影响的玩家体验。不得使用“功能正常”“表现正确”等模糊条件，也不得写代码、类名、API、数据结构、内部日志、技术接入步骤或以实现细节作为通过条件。策划案确实不涉及程序功能时，本节明确写“本策划案不涉及程序功能验收”并说明范围依据，不创建占位编号。

同一需求同时包含资产品质与运行时行为时，第 6.2 节和第 6.3 节分别建立独立验收项，并用文字互相标明关联编号；不得把同一个通过条件复制到两个小节，也不得用一个小节的通过结论代替另一个小节。

### 7. 实现方式建议（可选）

只有用户明确要求在策划案中记录实现方式建议时，才追加 `## 7. 实现方式建议`；用户没有提出该要求时，整章直接跳过，不写标题、占位说明或“无”。本章只覆盖用户明确指定或明确要求给出建议的实现范围，不主动扩展到其他技术主题，不为了补充本章读取代码、配置、程序文档或调查当前实现，也不把推测写成现状事实。

本章内容是非约束性的建议，不是实施 Plan、技术定案或完成证明。用户只要求记录其给出的建议时，忠实整理原意，不擅自增加方案；用户明确要求提供建议时，可以基于本轮允许读取的材料给出有限建议，并清楚标明待实施阶段核验的假设。除本章外，其他章节仍不得混入代码、类名、API、数据结构、生命周期、资源导出步骤或技术接入内容。

本结构适用于新建策划案和下一次发生实质修订的既有策划案。历史 `Completed` 策划案不因规范升级自动回退状态或批量改写；需要重新设计或实施时，把原美术资产验收与程序功能验收迁入第六章对应小节，尽量保留原 `ART-`、`FUNC-` 编号，并按本 skill 的状态流程处理。

六个必选章节和按条件出现的第七章都可以记录未来内容，但必须用 `state` 和正文措辞清楚区分仍在设计、等待实现、实现中、告警结束与已经完成的内容。正文中不得同时保留已经不再采用的旧规则。除用户明确要求的第七章外，不得出现代码块、伪代码、类名、API、调用链或技术实现 Todo；第七章也不得把建议写成已确定的实施任务或完成结论。

## 维护流程

1. 先按 `project-state-preflight` 的策划案分支分析真实需求与文档粒度，并在任务检查清单中写明建议篇数、每篇范围及拆分/合并理由。
2. 根据已确定的文档边界，读取目标策划案、其直接引用的 `AutoDoc/DesignPlan/media/` 图片、用户指定材料，以及 `AutoDoc/Design/`、`AutoDoc/Art/` 下直接相关的文档与图片；不要顺带遍历其他策划案、无差别加载媒体或调查代码实现。
3. 新建时使用当前 `YYYY.MM.DD` 目录和英文 kebab-case 文件名；修改时保留既有归档目录和文件名，除非用户明确要求迁移或重命名。
4. 检查文件头；新建或实质修改时使用 `state: In Design` 的三行文件头，并填写合法 `priority`。本轮写作完成后逐篇展示优先级并向用户确认是否定稿，只把用户明确确认的文档改为 `state: Todo`。`In Progress` 的三行文件头只由策划案实现流程在步骤 a 开始制定 Plan 前写入；`Warning` 与 `Completed` 的五行文件头只由该流程在步骤 g 写入。
5. 严格按六个必选章节创建或修改正文；第六章必须包含验收方式、美术资产验收、程序功能验收三个固定小节；只有用户明确要求记录实现方式建议时才追加第七章，未要求时整章跳过。除仅描述程序侧需求或配置侧需求的策划案外，为每篇策划案完成至少一张可用的现有、生成或编辑后原型图。
