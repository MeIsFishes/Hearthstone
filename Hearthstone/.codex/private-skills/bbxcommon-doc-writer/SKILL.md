# BbxCommon 底层文档写作规则

本 skill 用于指导 BbxCommon 底层模块使用文档的编写和维护。

## 底层模块定义

底层模块指满足以下条件的模块：

1. 代码位于 `BbxCommon` 命名空间下，通常在 `Assets/Scripts/BbxCommon/` 中。
2. 服务于框架能力、基础设施或通用工具，而不是某个具体游戏业务规则。
3. 游戏业务逻辑通常只需要通过 API、基类、生命周期钩子、配置或少量约定使用它，不需要理解其内部实现。

如果某个内容虽然被业务层频繁调用，但本质上是框架能力，也归入底层模块，例如 ECS、UI、GameStage、Task、资源管理、配置数据、对象池等。

本 skill 的四章节结构只用于介绍某个 BbxCommon 模块如何被业务代码使用。用于约束修改流程、文档格式或专项维护工作的工作流 skill，例如 `bbxcommon-doc-writer`、`bbxcommon-ui-item`，不套用模块使用文档结构。

## 输出位置

底层文档以 skill 的形式写入 `.codex/private-skills/`。

每个底层模块原则上对应一个 skill，skill 文件夹名必须以 `bbxcommon-` 开头，例如：

```text
.codex/private-skills/bbxcommon-ecs/
.codex/private-skills/bbxcommon-ui/
.codex/private-skills/bbxcommon-game-stage/
```

新建文件夹、`.md` 文件和子目录时，路径名使用英文小写、数字和连字符，避免系统路径问题。正文和标题使用用户的语言。

## 模块 Skill 结构

每个 BbxCommon 模块使用 skill 必须包含：

```text
bbxcommon-module-name/
├── SKILL.md
├── new-class-examples/
└── developer-docs/
```

- `SKILL.md`：模块主入口，供业务开发者快速了解如何使用该底层模块。
- `new-class-examples/`：如果该模块要求业务开发者新建类文件，在这里放代码模板、字段/函数要求和注意事项。
- `developer-docs/`：如果需要修改底层模块本身，在这里放更详细的调用链路、架构设计、生命周期、数据结构和风险说明。

如用户需求需要更多子文档，可以新增其他英文子目录或 `.md` 文件，但必须从 `SKILL.md` 关联过去。

## SKILL.md 必填内容

模块主文件 `SKILL.md` 必须包含 YAML frontmatter，且只写 `name` 和 `description`。

正文必须包含以下四节，顺序固定。由于底层问题复杂，如果用户要求增加章节，则按用户要求修正：

## 1. 模块概览

说明如何定义当前模块，以及它服务于游戏中的什么场景。

写作重点：

- 这个模块解决什么问题。
- 业务开发者在什么情况下会用到它。
- 它与其他 BbxCommon 模块的边界是什么。

## 2. API接口

本节直接说明模块的最简业务逻辑，并列出完成这个最小闭环必须使用的核心入口。不要在章节 2 下增加 `2.1` 等子章节。

编写顺序：

1. 先说明业务代码应通过哪些公开 API、基类或扩展方法使用模块，以及不应直接访问哪些底层管理类。
2. 用简短文字解释最简逻辑模型：核心对象各自负责什么、业务代码如何组合这些对象完成一次最小可用功能。
3. 再列出这个最简模型必需的 API、基类入口、Attribute、GameStage 注册项或生命周期钩子。
4. 只在缺少前置条件会导致最简模型无法运行时，补充对应前置条件。

接口范围必须保持克制：

- 只保留完成最简业务闭环必需的入口，不把“所有公开 API”当作目标。
- 查询、分组、绑定、兼容层、编辑器辅助、特殊变体和其它可选能力通常属于杂项，不在本节枚举；确有必要时放入对应业务类说明或子文档。
- 不设置“杂项接口”“其它接口”等子章节。
- 不解释程序底层调用顺序、内部管理器如何转发、缓存或对象池实现；这类内容放入 `developer-docs/`。
- 可以说明业务对象之间的职责关系与最小使用方式，但不要把源码调用链写进主文件。

如果模块没有集中 API 类，就按实际使用方式列出最简模型需要的基类、Attribute、GameStage 注册项或生命周期入口，不要为了格式编造 API。

## 3. 业务类

说明业务代码是否需要新建类文件。

如果需要新建类，必须说明：

- 类名或基类命名规则。
- 每种业务类负责什么功能。
- 这些类如何被框架发现、注册、加载或调用。
- 对应的新建类示例文档路径，链接到 `new-class-examples/` 下的子文档。

例如 UI 模块可能需要新建 `UiController` 和 `UiView`；ECS 模块可能需要新建 `EcsRawComponent`、`EcsMixSystemBase` 派生类或 `EcsRawAspect`。

如果当前模块不需要业务侧新建类，写明“当前模块通常不需要业务侧新建类”，并说明业务侧如何使用现有 API 或配置。

## 4. 主要类的生命周期

写业务开发者编写代码时最需要理解的主要类生命周期，尽可能简短。

写作重点：

- 列出该模块最重要的 API 类、业务基类、数据类、配置类或生命周期宿主。
- 对每个主要类说明创建、初始化、运行时使用、卸载或销毁阶段。
- 说明业务开发者应该在哪个阶段写入字段、注册回调、调用 API、释放资源或避免操作。
- 不要把完整源码走读堆在主文件里。
- 把底层详细调用链路、架构设计和复杂生命周期说明链接到 `developer-docs/` 下的子文档。

## 子文档写法

### new-class-examples/

当模块需要业务侧新建类时，为每种常见新建类写一个子文档。

业务类示例面向“如何正确新建并填写这个类”，不用于解释底层调用链。除非某个字段或函数为什么必须存在只能通过关键调用链说明清楚，否则不要讲框架内部如何逐层调用；这类内容应放入 `developer-docs/`。

业务类示例只解释当前类本身相关的内容：字段、函数、重写点、模板和注意事项。不要写“常用写法”、外部 API 调用示例、注册示例或其它类的使用流程。

子文档建议包含：

1. 使用场景。
2. 最小代码模板。
3. 必填字段、必填生命周期函数或必填重写函数。
4. 这些字段和函数为什么必须填写；如果原因很直观，可以只写简短说明。
5. 可选字段和可选函数，以及什么时候需要它们。
6. 常见错误和注意事项。

如果用户只要求建立模块主文档，而当前信息不足以写代码模板，可以先创建目录并在 `SKILL.md` 的“业务类”章节标注待补充，不要编造不存在的 API。

### developer-docs/

用于底层维护者阅读。可按模块差异灵活组织。

常见子文档包括：

- 类关系。
- 数据结构和缓存结构。
- 生命周期。
- 导入导出流程。
- 加载卸载链路。
- 与 Unity、DOTS、资源系统或 GameStage 的耦合点。
- 修改底层模块时的风险和回归检查点。

开发者文档可以比主文件更细，但仍要围绕当前模块，不要写成全项目说明。

## 执行流程

1. 任务开始时把本流程要求加入 `AutoDoc/Temp/` 下的任务检查清单；执行中不要求逐项更新，结束前统一复核并写任务报告。
2. 确认目标模块属于 BbxCommon 底层模块，而不是游戏业务模块。
3. 搜索 `Assets/Scripts/BbxCommon/` 和现有 `bbxcommon-*` skill，确认模块 API、业务类、主要类生命周期和开发者细节。
4. 创建或更新 `.codex/private-skills/bbxcommon-<module>/`。
5. 确保该模块 skill 具备 `SKILL.md`、`new-class-examples/`、`developer-docs/`。
6. 编写 `SKILL.md` 四个必填章节，并把所有子文档链接进去。
7. 根据用户需求补充子文档；如果新增子文档，回到 `SKILL.md` 增加链接。
8. 检查 API 章节没有子章节、杂项接口或底层调用顺序，并确认所列入口足以完成文中描述的最简逻辑模型。
9. 检查 `description` 简短清楚，路径名英文，正文使用用户语言。
10. 汇报新增或更新的 skill 路径、子文档路径、缺失信息和待确认项。
