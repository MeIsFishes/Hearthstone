如果用户要求输出方案但不要求实际修改项目，在任务开始时把以下条目写入本次 `*-Checklist.md`。方案草稿和最终方案文档统一保存在 `AutoDoc/Temp/Plan/`；目录不存在时先创建。

确保任务结束时审计这些项，在同文件中总结检查结果并修正。

1. 按照 `AGENTS.md` 中的文档目录定位方案直接相关的程序、美术和玩家视角设计文档，只把它们作为当前现状依据，不进行修改。`AutoDoc/DesignPlan/` 通常没有参考价值；除非用户明确指定某篇策划案作为输入、方案本身针对策划案，或用户要求追溯设计决策，否则不要搜索、枚举或读取该目录。即使读取，也只把它作为设计意图而非当前现状依据。
2. 将用户要求和适用 skill 的约束全部加入检查清单，并据此形成确定、可执行且内部一致的方案。
3. 将方案草稿和最终方案文档写入 `AutoDoc/Temp/Plan/`；如果设计的是游戏内功能，按 `.codex/private-skills/plan-output-format/SKILL.md` 检查结构和 Todo。
4. 复核方案的范围、依赖、实现顺序、验证方式和 Todo，修正含糊、冲突或并存的多套实现路线。
5. 审计方案是否绕过项目框架；发现框架外设计时反复修订到框架内。框架能力不足时，小改动可作为明确的框架 Todo 纳入方案，大改动必须标为需先向用户上报并确认，不能静默设计成业务层绕行。

任务结束前按 `project-state-preflight` 主文件逐项复核这些条件，并在独立报告中记录证据。
