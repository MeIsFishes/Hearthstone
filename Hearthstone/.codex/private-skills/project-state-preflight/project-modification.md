如果用户要求修改项目，在任务开始时把以下条目写入本次 `*-Checklist.md`。本流程也适用于按照普通方案执行项目修改；只输出方案而不修改项目时使用 `solution.md`，不得把尚未实现的方案写入当前状态文档。创建、重写或更新正式策划案由 `design-plan-writing.md` 接管；按照正式策划案修改游戏由 `design-plan-implementation.md` 接管。这两类任务都不使用本流程。

确保任务结束时审计这些项，在同文件中总结检查结果并修正。

1. 将用户要求、适用 skill 的约束，以及既有方案中本次需要实现的 Todo 全部加入检查清单。
2. 完成修改，并检查是否误改无关文件、遗漏直接依赖或绕过项目既有框架；发现框架外实现时必须持续整改并重新审计，不能以兼容补丁结束任务。
3. 涉及代码时，检查新增函数和字段是否确有复用价值，删除不必要的一次性抽象。
4. 完成项目修改和必要验证后，把文档同步作为结束门槛，逐类核对玩家视角设计、美术和程序文档：
   1. 必须完整读取 `.codex/private-skills/design-doc-format/SKILL.md`、`.codex/private-skills/art-doc-writer/SKILL.md`、`.codex/private-skills/program-doc-format/SKILL.md`。当前主题命中更具体的项目级或底层文档 skill 时，只检索与本次模块直接相关的 skill 元数据，再完整读取适用 skill 及其要求的格式引用；不得套用不相关格式。
   2. 以本次实际代码、配置、资源、验证证据和玩家可见结果确定文档影响，不以用户需求、普通方案、旧文档或未落地预期代替当前现状核验。只处理本任务直接相关范围。
   3. 在检查清单中分别列出“玩家视角设计文档”“美术文档”“程序文档”三项；每项记录已读取的基础与专项 skill、现有相关文档、实际现状变化、处理结论、目标文档路径和核验证据。
   4. 现有相关文档需要同步时，必须按适用 skill 在本任务内实际更新；本次实现形成新的独立文档范围且不存在对应文档时，必须按适用 skill 实际新增。不得只在检查清单或报告中写“建议更新”“后续补充”或遗留文档 Todo 后结束任务。
   5. 某类文档确实不受本次修改影响时，可以标记“不适用”，但必须写明基于实际修改范围和核验证据的理由；不得因为现有文档缺失、修改麻烦或任务没有显式点名文档就跳过。
   6. 新增或更新的正式文档只记录已经实现且可由项目确认的当前现状，并遵循适用 skill 的路径、格式、语言、媒体和范围边界。`AutoDoc/DesignPlan/` 通常没有参考价值，也不属于本门槛的默认读取或同步范围；只有用户明确指定某篇策划案作为本次实现输入时才读取，并且不能把它作为当前实现的核验依据。
5. 若框架能力不足，记录能力缺口与影响范围：小型、局部、向后兼容的框架改动可直接完成并验证；涉及公开契约、核心生命周期、数据/资产格式或多模块影响的大改动，必须先上报用户并取得许可。

任务结束前按 `project-state-preflight` 主文件逐项复核这些条件，并在独立报告中记录证据。
