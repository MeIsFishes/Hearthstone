# Project State Preflight

在每次对话前，先使用这个 skill。
你应当使用用户的语言输出文档。

每次用户触发对话时，按以下顺序分类，并在匹配后停止：

1. **编写策划案**：用户明确要求创建、重写或更新正式 `AutoDoc/DesignPlan/YYYY.MM.DD/` 策划案文档。该类型虽然会修改项目文件，但优先于普通“修改项目”匹配。`AutoDoc/DesignPlan/Plan/` 的实施 Plan 和 `AutoDoc/DesignPlan/Review/` 的实现审查文档不是策划案正文；只讨论策划案方向、分析需求或评审现有策划案而不写正式文件时，也不匹配本类型。
2. **实现策划案**：用户明确要求按照一篇或多篇正式 `AutoDoc/DesignPlan/YYYY.MM.DD/` 策划案修改游戏，或要求实现该范围内的策划案。该类型优先于普通“修改项目”匹配；`AutoDoc/DesignPlan/Plan/`、`AutoDoc/DesignPlan/Review/` 和普通 `AutoDoc/Temp/Plan/` 中的文档本身都不是可独立选择的正式策划案。
3. **修改项目**：用户要求修改项目中的代码、配置、资源、普通文档、skill 或其他文件，也包括实现普通方案和修复问题；正式策划案写作与实现已经由前两个类型接管。
4. **要求出方案**：用户要求计划、设计或实现方案，但不要求实际修改项目内容。方案文档可以写入 `AutoDoc/Temp/Plan/`，不因此改判为修改项目。
5. **纯问答**：用户只要求回答、解释、分析、诊断、审查或汇报状态，既不要求修改项目，也不要求输出方案。

## 检查清单与报告

“编写策划案”“实现策划案”“修改项目”和“要求出方案”在开始实质性工作前执行：

1. 在项目根目录 `AutoDoc/Temp/` 创建本次任务专用的 `*-Checklist.md`。
2. 读取匹配类型的流程文件，把其中条目、用户要求和适用 skill 的检查项写入清单；适用 skill 未提供检查项时，根据任务目标补齐。
3. 一次性写入当前已知检查项后开始工作。清单不规定实际执行顺序，不要求执行期间逐项勾选；可以按依赖关系调整顺序、批量处理或并行处理。
4. 执行中发现新的风险或约束时追加检查项。只有用户明确要求分阶段确认时，才在指定确认点暂停。

“实现策划案”的选案与逐篇实施步骤是必须严格遵守的流程门槛，不受上面“清单不规定实际执行顺序”的通用说明影响。该流程要求的用户确认、单篇内部顺序和审查通过条件不得跳过或合并；多篇策划案按 `design-plan-implementation.md` 的专属规则逐篇实施。

每份检查清单都必须包含“框架边界审计”，并按以下规则执行：

1. 检查方案与实现是否绕过项目已有框架、公开 API、生命周期、编辑器配置源或导出流程，是否在业务层重复实现框架已经提供的能力。
2. 一旦发现框架外代码或框架外资产流程，不得把兼容补丁、临时绕行或“当前能运行”判为通过；应继续修改并反复复核，直到业务实现被限制在项目框架内。
3. 若现有框架确实无法满足需求，先把问题收敛为最小的框架能力缺口：
   - **小改动**：局部、向后兼容、不改变核心生命周期或数据/资产格式、影响面可直接验证的修改，可以直接修改框架，并把框架改动与回归证据写入检查清单和报告。
   - **大改动**：新增或破坏公开契约、改变核心生命周期、数据/序列化/导出格式，或影响多个模块和大量既有调用方的修改，通常必须先向用户上报缺口、影响范围和拟议方向，得到明确许可后再修改框架。唯一例外是“实现策划案”：该类型按 `design-plan-implementation.md` 的专属默认授权规则直接实施，不因框架修改授权问题暂停，并在最终正式 Review 中完整记录。
4. 无论修改业务层还是框架层，结束审计都要重新检查是否仍残留平行实现、手写导出产物或对框架内部管理器的绕过访问；仍存在时该项保持未通过。

“编写策划案”不读取代码或程序文档，其框架边界审计只检查策划案是否越过策划职责、在非用户明确要求的可选第七章“实现方式建议”中写入技术实现，或建立平行文档/媒体流程；不得为了完成该审计调查代码或判断框架能力。

任务结束前必须执行：

1. 重新读取检查清单，逐项对照实际文件、命令结果或其他证据进行复核。
2. 将每项标记为通过、未通过或不适用，并在条目下写简短证据。不能只凭“做过了”判定通过。
3. 对可修正的未通过项先完成修正，再重新复核；无法修正的项保留未通过状态并写明阻塞原因。
4. 只执行一次项目根目录下的 `AutoDoc/CleanupTempDocs.bat`；不要在执行过程中重复运行，并记录退出结果。
5. 清理后在 `AutoDoc/Temp/` 创建同任务名的 `*-Report.md`。报告至少包含任务结果、检查项结果与证据、验证结果、执行偏差、未解决风险、文档处理和清理结果。

“纯问答”不创建检查清单，没有额外流程要求；直接按用户请求回答。如果后续请求转为“编写策划案”“实现策划案”“修改项目”或“要求出方案”，再创建对应检查清单。已经创建清单的任务即使阻塞或提前结束，也要完成结束复核并写报告。

## 类型路由

根据分类读取一个流程文件：

- 编写策划案：`design-plan-writing.md`
- 实现策划案：`design-plan-implementation.md`
- 修改项目：`project-modification.md`
- 要求出方案：`solution.md`
- 纯问答：不读取流程文件
