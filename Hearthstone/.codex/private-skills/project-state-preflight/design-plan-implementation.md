# 实现策划案流程

本流程用于实现一篇或多篇正式 `AutoDoc/DesignPlan/YYYY.MM.DD/` 策划案。实施 Plan 与最终 Review 分别保存到 `AutoDoc/DesignPlan/Plan/`、`AutoDoc/DesignPlan/Review/`，两者不是候选策划案。开始前把本流程要求写入任务检查清单。

单篇策划案严格按 a 至 h 执行；多篇策划案按照已确定的顺序逐篇完成。策划案第 6.1 节指定验收方式，第 6.2 节的 `ART-` 美术资产验收与第 6.3 节的 `FUNC-` 程序功能验收必须分类追踪，不得在 Plan、审查或 Review 中混为无类别清单。

验收方式只分为“流程log验收”“游戏内截图”“仅功能验收”三种，策划案未指定时默认流程log验收。流程log验收与游戏内截图都必须由主代理显式进入对应游戏场景并完成实际操作；仅功能验收不进入游戏，只能直接调用实际功能入口或使用最小范围的一次性轻量脚本取得可判定输出。策划案不要求游戏内截图时，美术验收由主代理检查相关资产编排完成。同一策划案可按验收点组合多种方式，共享同一进入路径和操作链的同类验收点可以合并为一趟执行，但必须保留“验收趟次 → case → 原 `ART-`/`FUNC-` 编号”映射，且美术资产与程序功能仍分别判定。不得为验收引入新的测试框架或大型测试模块；验收专用临时脚本及其测试专用附属文件在验收结束后必须删除。

允许在当前正常分支直接提交，并在存在唯一 upstream 时推送；无 upstream 时记录“推送不适用”。

## 代理分工

1. Plan 与代码由注册表中的专用子代理独立审查；`design_plan_code_reviewer` 只负责代码审查，不执行验收或编写正式 Review。主代理负责传递审查意见，并独立完成验收、验收结论和正式 Review。
2. 开发完成后，主代理按策划案第 6.1 节指定的方式执行验收；未指定时使用流程log验收。流程log验收与游戏内截图必须按 `test-game-content` 通过正式 StageGroup 入口显式操作 Unity，不得用后台 Unity、静态检查或子代理结论冒充；仅功能验收只允许直接功能入口或最小一次性轻量脚本。未要求游戏内截图时，美术验收改为检查实际资产内容与相关资产编排。验收 case 只可在同类别内合并，跨类别 case 保留关联。任一主干失败后最多执行两趟“修改、code reviewer 复审，并在无代码硬阻塞时由主代理重新验收”；每趟只调用一次 code reviewer，不得自动增加第三趟。
3. 确认框架能力不足时，当前策划案所需的框架修改默认已授权，不因规模或授权问题询问、暂停或追认。改动仍须纳入 Plan、审查和验证，不得夹带无关需求，并在最终 Review 记录缺口、改动、影响、兼容性和回归证据。
4. 每篇策划案处理结束时，主代理必须关闭为该篇启动的所有审查子代理，终止仍在运行者并确认没有活动遗留；不得留给下一篇复用。

## 一、辨认、调查并排序待处理策划案

1. 先确认用户指定的是范围还是明确文件；无法唯一确定时询问，不得猜测。
2. 范围选择只枚举 `AutoDoc/DesignPlan/YYYY.MM.DD/*.md`，读取前三行 `title:`、`state:`、`priority:`，纳入等待开始的 `Todo` 和需要续跑的 `In Progress`；排除 Plan、Review、`In Design`、`Warning` 和 `Completed`。
3. 明确文件可纳入 `Todo` 或 `In Progress`；`In Design` 需在清单标注；`Warning` 与 `Completed` 必须二次确认。文件必须位于正式日期目录。
4. 文件缺失、头部错误、状态不在 `In Design`/`Todo`/`In Progress`/`Warning`/`Completed`、优先级不在 `P0`/`P1`/`P2` 或范围冲突时先确认。`In Progress` 必须使用严格三行文件头；`Warning`、`Completed` 的 `plan:`、`review:` 路径需验证，重新实施时在步骤 a 移除并在步骤 g 写入当前最终路径。
5. 对每篇 `In Progress` 策划案，盘点既有 Plan、审查记录、实现改动、验收材料、Review、Git 状态和检查清单证据，确定 a 至 h 中最早尚未完成的门槛；只复用可追溯且仍与当前内容和改动一致的产物，不因状态本身假定任何步骤已完成，也不重复创建已有 Plan。
6. 排序前阅读全部候选需求及判断依赖所需的当前代码、配置、资源和现状文档；此阶段只调查、排序和判断恢复点，不实施，也不得修改策划案状态。
7. 主代理综合优先级、目录日期、硬依赖、共享改动和回归风险确定实施顺序；偏离直观优先级或日期顺序时说明理由。
8. 在进度说明和检查清单列出候选、过滤结果、实施顺序及依据，完成后才进入实施。

## 二、逐篇严格实施

每篇严格依次通过 a 至 h，完成当前篇后再开始下一篇。

### a. 输出实施 Plan

1. 即将开始制定实施 Plan 时，主代理必须先把本篇第二行改为 `state: In Progress`；候选筛选、调查和排序阶段不得提前切换。`Todo`、已明确纳入实施的 `In Design`、经二次确认重新实施的 `Warning` 或 `Completed` 都执行此切换；从 `Warning` 或 `Completed` 切换时同时移除旧 `plan:`、`review:` 行，恢复严格三行文件头。状态写入或文件头复核失败时不得开始制定 Plan。已经是 `In Progress` 的续跑文档不重复改写，只复核严格三行文件头并按调查阶段确定的最早未完成门槛继续。
2. 把状态切换、原状态、时间和恢复点记录到检查清单，并且只读取当前策划案及其必要现状材料。
3. 按 `game-module-design` 与 `plan-output-format` 创建或继续更新 `AutoDoc/DesignPlan/Plan/<document-name>-plan.md`。Plan 先记录第 6.1 节的验收方式，未指定时使用流程log验收；再单独建立美术资产验收覆盖，列出第 6.2 节 `ART-` 稳定编号、资产落点与检视方式；单独建立程序功能验收覆盖，列出第 6.3 节 `FUNC-` 稳定编号、功能落点与验证方式。不得建立混合覆盖，不夹带无关需求；缺少可判定的核心验收条件时先请用户补充。既有 Plan 只有在与当前策划案和现状一致时才继续使用，否则在原路径修订，不另建重复 Plan。

从步骤 a 开始直到步骤 g 将本篇设置为 `Completed` 或 `Warning` 前，本篇保持 `In Progress`。Plan、审查、实现、验收或正式 Review 形成过程中断、失败或阻塞时不得自动回退为 `Todo`，并在检查清单与报告中记录最后完成门槛和继续入口；只有策划内容需要重新设计时，才按策划案写作流程恢复为 `In Design`。

### b. 由子代理审查 Plan

1. 使用 `design_plan_plan_reviewer` 按 `.codex/agents/design-plan-plan-reviewer.toml` 独立只读审查。提供第 6.1 节验收方式、第 6.2 节 `ART-` 验收编号与第 6.3 节 `FUNC-` 验收编号，再提供 Plan、范围、框架规则和必要现状证据；审查细节以该 TOML 为准。
2. 每篇 Plan 默认只进行一次独立审查。主代理评估意见，完成成立项的修改，并结合新 Plan、原审查意见和针对性证据核对修正结果；不得为了取得 `通过` 结论而自动反复调用同类审查。仍有未解决的需求、框架或可执行性硬阻塞时不得实施。

### c. 执行已通过审查的 Plan

1. 按已通过 Plan 和适用项目 skill 修改，使用既有框架与公开接口，禁止兼容补丁、平行系统、手写导出或绕过内部管理器。
2. 完成必要的静态检查和编译确认并记录证据，用于排除基础错误；不得把开发期验证扩展成新的测试框架或大型测试模块。实际验收按步骤 e、f 执行。Plan 发生实质变化时同步更新，并按原审查关注点核对变化；不自动返回步骤 b。若变化引入新的未解决硬阻塞，则暂停实施并报告。

### d. 由子代理审查实际改动

1. 使用 `design_plan_code_reviewer` 按 `.codex/agents/design-plan-code-reviewer.toml` 只审查代码、配置与资源接入。提供策划案、Plan、预期实现范围、排除项、遗留改动、框架上下文、Git 基线、轮次和唯一输出 `AutoDoc/Temp/<document-name>-code-review-round-<round>.md`；不得要求其执行验收、判断验收通过或写入正式 Review，审查细节以该 TOML 为准。
2. 每篇实际改动先进行一次全面代码审查。首次审查通过时结束本阶段代码审查；首次审查不通过时，主代理逐条评估意见，完成成立项的修正，并结合代码和证据处理异议，修正完成后最多再进行一次代码审查，重点核对原意见、修正差异及其引入的新问题。第二次审查结束后由主代理执行差异核对与针对性验证，不得在本阶段自动发起第三次代码审查；只有用户明确要求时才可突破本阶段上限。
3. 框架不足按默认授权修正；框架外实现不得进入验收。代码审查 `通过` 只表示代码审查通过，不代表策划案验收通过。保留实际发生的审查意见和处理记录，供主代理在步骤 f 编写正式 Review 时引用。步骤 f 因验收失败而产生的修改必须按其失败回路额外执行针对该趟差异的一次代码复审；这些复审不计入本步骤的初始两次上限，但严格受失败回路最多两趟、每趟一次复审的限制。仍有未解决的正确性、安全性或框架硬阻塞时暂停并报告。

### e. 规划本篇验收

步骤 e、f 共同构成验收阶段，必须依次完成：1）确认本篇 a 至 d 的进度和阻塞项；2）列出验收方式和验收列表；3）规划验收的预计趟数、游戏场景和操作；4）由主代理正式验收，主干失败时执行最多两趟修改、代码复审和重新验收，最后根据验收材料提交正式 Review。前三项没有完成时不得开始第四项。

正式验收前，主代理必须在检查清单和进度说明中完成以下三项：

1. **确认本篇进度**：列出 a 至 d 的完成状态、阻塞项和是否已具备验收条件。
2. **列出验收方式与验收列表**：列出第 6.1 节要求的验收方式，未指定时写明默认流程log验收；分别列出第 6.2 节 `ART-`、第 6.3 节 `FUNC-` 和受影响旧功能回归点，标记主干/非主干、操作、预期、证据类型与 case 映射。不涉及某类时保留策划案依据，不创建占位编号。
3. **规划验收趟次**：把可共享进入路径和操作链的项目编成稳定的验收趟次编号，明确预计总趟数、每趟进入的游戏场景、按顺序进行的操作、采用的验收方式、产生的证据，以及该趟覆盖的 case 和原 `ART-`/`FUNC-` 编号。仅功能验收不进入游戏时将游戏场景标为“不适用”，并写明直接功能入口或一次性脚本。允许同一趟同时取得美术资产和程序功能证据，但必须分别建立 case 和结论，不得建立跨类别混合 case。

主干至少包括实现策划案核心目标所必需的资产、功能链路，以及一旦失败就会使核心链路不可用的关键旧功能回归；不得为了降低完成门槛将其降为非主干或“边界情况”。只有少数不影响核心链路的边界项可以列为非主干。主干/非主干分类必须在首次正式验收前按策划案目标和核心链路证据确定，不得只因某项验收失败或困难而事后降级；只有新的设计证据证明原分类错误时才能更正并记录理由。非主干项难以取得可靠证据、验收成本明显不成比例、不准备单独执行或实际未通过时，必须预先说明或在验收中如实记录，不得默认为通过，但不单独阻塞 `Completed`。

### f. 由主代理正式验收并提交验收 Review

主代理不得把以下验收操作、通过判定或正式 Review 写作委托给 Plan reviewer 或 code reviewer。

1. **准备正式入口与证据映射**：按步骤 e 的验收趟次建立记录，先写明趟次编号、策划案、case、原 `ART-`/`FUNC-` 编号、预期结果和证据位置。流程log验收或游戏内截图涉及进入游戏时，完整读取并遵循 `test-game-content`，查找或创建符合框架规则的 StageGroup 入口，通过 `GameStageEntryLauncher` 启动；禁止手动打开内部 Scene、绕过 StageGroup 或另建 Play Mode 调度。
2. **执行流程log验收**：通过正式 StageGroup 入口进入计划场景，记录启动时间、入口参数与初始状态，并从本次启动时间或当前日志读取位置隔离旧运行记录；严格按验收趟次的顺序完成玩家操作。采集 Unity Console、Editor Log 或实际流程明确输出的本次 Log，保存到 `AutoDoc/Temp/<document-name>-<trip-id>-flow-log.md`，并按“操作步骤 → 关键 Log → 预期结果 → 实际结果 → 覆盖 case/编号”整理证据；Log 必须能够区分本趟操作并直接支持结论，缺少、混入旧运行记录或无法映射时不得判定通过。
3. **执行游戏内截图验收**：通过正式 StageGroup 入口进入计划场景，完成规定操作并停留在能够证明验收条件的玩家可见状态。截图必须来自本次实际运行，归档到 `AutoDoc/DesignPlan/media/YYYY.MM.DD/<document-name>/review/`，使用英文小写 kebab-case 文件名，并记录“截图 → 场景 → 操作 → case/编号”映射；模糊、遮挡、状态不完整或无法对应本篇的截图不得作为通过证据。
4. **执行仅功能验收**：不进入游戏场景，只调用生产代码的实际功能入口或使用最小范围的一次性轻量脚本，输入明确参数，并把调用入口、输入、预期、实际输出与覆盖编号保存到 `AutoDoc/Temp/<document-name>-<trip-id>-functional-result.md`。不得复制生产逻辑、伪造运行结果或建立平行实现；静态检查、编译成功或函数存在不能单独作为功能通过证据。
5. **执行美术资产验收**：策划案要求游戏内截图时，以本次截图和对应实际资产共同判断 `ART-`。策划案不要求游戏内截图时，不进入游戏补拍图片，改为检查相关资产编排：逐项确认实际资产路径、资产或资产组内容、引用与组合关系、层级/布局/状态编排、规格与状态覆盖是否对应 Plan 和 `ART-` 通过条件，并记录“美术资产 case → 原 `ART-` 编号 → 资产路径 → 编排位置/关系 → 检查结果”。只有文件存在而没有正确编排，或编排证据无法覆盖通过条件时不得判定通过。
6. **记录分类结果**：按“验收趟次 → 策划案 → 美术资产 case/程序功能 case → 原稳定编号”逐层记录结果。美术资产与程序功能分别判定；同一趟证据可以复用，但不得用程序功能结论代替美术编排或玩家可见品质，也不得用截图、资产存在或代码审查通过代替程序行为闭环。
7. **清理每趟验收材料**：仅功能验收脚本和进入游戏所用的一次性启动脚本必须保持最小范围。每趟验收结束后，无论通过、失败或阻塞，都删除验收专用临时脚本及其测试专用附属文件，并检查文件与 Git 状态确认无遗留；正式功能脚本不在此删除范围。
8. **执行最多两趟验收修正回路**：首次验收中任一主干 `ART-`、`FUNC-` 或关键回归未通过或缺少足以判定通过的证据时，先把失败原因、证据、阻塞项和修正方向写入 `AutoDoc/Temp/<document-name>-acceptance-review-attempt-<attempt>.md`，其中 `<attempt>` 依次使用 `initial`、`retry-1`、`retry-2`，再开始修正趟次 1；每一趟必须严格完成以下闭环：
   1. 根据本趟验收失败证据修改必要的实现与 Plan，并记录本趟差异。
   2. 修改后使用 `design_plan_code_reviewer` 对本趟差异进行一次代码复审；`<round>` 从步骤 d 已使用的最后编号继续单调递增，输出新的唯一 round 文件，禁止覆盖既有审查记录。code reviewer 仍只审查代码、配置与资源接入，不执行验收、不判断验收通过、不编写正式 Review。
   3. 主代理逐条评估复审意见；成立项在当前修正趟次内继续修正，再核对最终差异与必要静态证据，本趟不追加第二次 code reviewer 调用。仍有正确性、安全性或框架硬阻塞时，本趟判为未通过且不得进入实际验收，不能用验收结论掩盖代码问题；否则更新步骤 e 的验收列表和趟次，再由主代理亲自重新执行失败的主干项及受影响的必要回归。
   4. 主干全部通过时立即结束失败回路；仍未通过时记录本趟 attempt，并明确写本趟“已重新验收”或“因代码硬阻塞未进入实际验收”。若只完成修正趟次 1 则进入修正趟次 2；修正趟次 2 后仍未通过时停止，不得自动发起第三趟修改、代码复审或重新验收。
   首次验收不计入这两趟修正次数；每趟只允许一次针对该趟差异的代码复审。非主干边界项验收困难或未通过不触发修正回路，按原编号、证据缺口、影响和后续决策需求写入正式 Review 的“待决策技术项”。
9. **由主代理形成结论**：主代理逐项复核实际证据。主干美术资产、主干程序功能和使核心链路可用的关键回归全部通过时，本篇验收结论为 `通过`，可以进入 `Completed`；少数非主干边界项未通过、难以取得可靠证据或未单独执行不改变该结论，但必须如实记录，不能写成通过。首次验收及两趟修正后主干仍未通过时，本篇结论为 `主干验收未通过`，进入 `Warning`。代码审查结论仅作为代码质量证据，不代替任何验收结论。
10. **由主代理编写正式 Review**：验收结论为 `通过` 时，主代理直接创建或更新 `AutoDoc/DesignPlan/Review/<document-name>-review.md`。验收修正次数尚未耗尽时只写 attempt 文件，不创建或覆盖正式 Review。两趟修正耗尽后主干仍未通过时，主代理必须在同一正式 Review 路径创建或更新结论为 `主干验收未通过` 的 Review，完整记录首次验收、两趟修改与代码复审、各次实际执行的验收证据、残留失败和影响，供步骤 g 设置 `Warning`。正式 Review 必须自足地摘录足以复核结论的关键证据与映射；可以引用临时证据路径，但不得把结论建立在可能被清理的 `AutoDoc/Temp/` 文件单独存在之上。

#### 正式 Review 固定结构

正式 Review 从 `## 1. 实现方式` 开始，不加一级标题、前言或其他二级章节，并遵循：

1. `## 1. 实现方式`：用不超过 100 个字符概括已经落地的主干实现，不展开审查过程或未采用方案。
2. `## 2. 验收`：固定包含以下三个小节：
   - `### 2.1 验收方式`：记录实际采用的方式、验收趟次、进入场景、操作、主要证据和覆盖 case。
   - `### 2.2 美术资产验收`：按美术资产 case 记录结果、原 `ART-` 编号和直接证据。未要求游戏内截图时，必须记录资产路径与资产编排检查证据；要求截图时嵌入位于 `AutoDoc/DesignPlan/media/` 的实际截图并写图注。
   - `### 2.3 程序功能验收`：按程序功能 case 记录结果、原 `FUNC-` 编号、操作或调用和直接证据。
   跨分类关联单独注明；非主干项未单独验证或未通过时如实记录，不得省略或写成通过。
3. `## 3. 待决策技术项`：逐项记录少数非主干边界项难以取得可靠验收证据、验收成本明显不成比例、未通过或未单独执行的情况，包含原编号、已取得证据、缺口、对玩家与后续开发的影响和需要决策的方向；也记录仍需用户选择且会实质影响公开契约、架构、生命周期、数据/资产格式或后续方向的技术风险。不得把主干失败移入本章来获得 `Completed`；没有任何待决策项时整章省略，后续章节仍编号为 4。
4. `## 4. 详细审查意见`：由主代理综合最终代码审查意见、验收修正各趟的复审与处理结论、实际验收、修改范围、框架能力缺口与改动、兼容或迁移处理、回归证据、特定需求 trick 评估和遗留风险，给出 `通过` 或 `主干验收未通过` 的最终结论；不得只写一句结论或粘贴大段 diff。

主代理复读正式 Review，确认第 1 章字数、第 2 章三个小节、每项证据与编号映射、图片路径、非截图美术编排证据、第 3 章待决策项边界和最终结论准确后，才能进入步骤 g。

### g. 完成策划案或标记 Warning

1. 主代理先按步骤 f 的正式 Review 确认终态：主干美术资产、主干程序功能和关键回归通过时选择 `Completed`，非主干边界缺口不单独阻塞；首次验收及两趟修正后主干仍未通过时选择 `Warning`。未完成规定验收、修正或正式 Review 时保持 `In Progress`，不得提前选择终态。
2. 正式 Review 形成后，按适用 skill 同步直接相关的 Program、Design、Art 现状文档；只记录已经由当前代码、配置、资源和证据确认的项目现状，不把 `Warning` 中未实现或未通过的目标写成现状。
3. 确认最终 Plan 与正式 Review 均存在并对应本篇。结论为 `通过` 时，将文件头更新为：
   ```text
   title: <原标题>
   state: Completed
   priority: <原优先级>
   plan: AutoDoc/DesignPlan/Plan/<document-name>-plan.md
   review: AutoDoc/DesignPlan/Review/<document-name>-review.md
   ```
   结论为 `主干验收未通过` 时，将文件头更新为：
   ```text
   title: <原标题>
   state: Warning
   priority: <原优先级>
   plan: AutoDoc/DesignPlan/Plan/<document-name>-plan.md
   review: AutoDoc/DesignPlan/Review/<document-name>-review.md
   ```
   两种终态均在第五行后空一行。复读验证五行、路径、正式 Review 结论和状态一致，并记录到检查清单；`Warning` 不算依赖完成，不得启动依赖其主干成功的策划案。

### h. 提交并按现有条件推送 Git 改动

1. 步骤 g 后检查 Git 根目录、当前分支和 upstream。未接入 Git 或 detached HEAD 时报告；不得自行初始化、切分支或改远端。
2. 按 Plan 和差异确认本篇文件，只用明确路径暂存；不得纳入既有、其他策划案、临时或构建改动，不得使用 `git add .` / `git add -A`。用户指定的正式策划案及其引用媒体即使未跟踪也可纳入；混合改动无法安全分离时请用户处理。
3. 复核暂存区后提交；无改动不建空提交。钩子产生新改动时返回步骤 d。
4. 仅在当前分支有唯一 upstream 时普通 push；禁止 force push、改历史或自动 pull/rebase/merge。无 upstream 记录“推送不适用”；推送失败时保留本地提交并报告。
5. 把 commit、分支、upstream、push 结果和提交后 `git status --short` 写入检查清单。其他尚未提交的任务内改动可以暂时存在，但必须逐项归属，不能被当前篇顺带提交。
6. 整个批次的全部策划案都完成提交后，`git status --short` 必须无输出；只要仍有已暂存、未暂存或未跟踪内容，就不得把策划案执行任务报告为完成。任务内改动返回相应步骤处理并提交；任务外遗留改动不得擅自提交、修改或丢弃，必须作为完成阻塞上报用户处理。
7. 本篇进入 `Completed` 或 `Warning` 并完成提交处理后，关闭其全部 Plan 审查和代码审查子代理，确认无仍在运行的本篇代理，并把结果写入检查清单。

## 三、批次收尾

1. 检查清单汇总每篇的 Plan/Review、初始代码审查、最多两趟验收修正与复审、框架改动、验收、`Completed`/`Warning` 文件头、Git 和子代理关闭证据。
2. 汇总步骤 e、f 已执行的验收趟次、场景、操作、证据和逐篇 Review，不在批次收尾另建一套验收。若正式验收后又出现会影响行为或资产结果的改动，必须使受影响 Review 失效，并返回步骤 d、e、f 完成差异核对、重新验收和 Review 后再提交。
3. 确认没有遗留活动审查子代理后，按 preflight 执行结束审计、一次清理和报告，汇总候选排序、逐篇产物、审查、框架改动、验收方式、验收趟次、验收 Review、状态、提交、推送与风险。
4. 报告创建后最后一次检查 `git status --short`；只有无输出时才能报告整个策划案执行任务完成。任务内遗留返回相应步骤处理；任务外遗留不得擅自提交或丢弃，保持未完成并向用户说明需要其处理的确切路径。
