如果用户要求创建、重写或更新正式策划案，在开始实质性写作前把以下内容写入本次 `*-Checklist.md`，并遵循 `.codex/private-skills/design-plan-doc/SKILL.md`。

## 需求拆分说明与意见

检查清单必须包含同名章节，并在创建任何正式策划案前写入实际分析结论，不能只列“待分析”检查项：

1. **真实需求摘要**：用玩家目标与期望体验重新表述用户需求，不照抄用户句子。
2. **需求分块**：列出独立功能点、所属模块、对应游戏场景、与其他功能点的依赖或耦合，以及是否可以独立设计和验收。
3. **文档建议**：明确建议写成几篇策划案；为每篇给出拟定 `title`、英文文件名、归档路径、`P0/P1/P2` 优先级建议及理由、覆盖的功能点和范围边界。
4. **拆分与合并理由**：说明为什么相关功能可以合并，为什么其他功能必须拆分；不得用“用户一次提出”作为合并理由。
5. **主代理意见**：指出需求过宽、跨模块、隐含冲突、缺少输入或可能需要后续独立策划案的部分，并说明本次采用的合理假设。

默认一篇策划案对应一个功能点，或同一模块内强关联、必须共同解释的功能点集合。不同模块、不同玩家目标、不同场景或可独立验收的功能默认拆篇。更新既有策划案时，也要先判断新增内容是否仍属于原文档范围；不属于时新建文档。

## 写作检查项

把以下条目连同用户要求和适用 skill 约束一次性加入检查清单：

1. 只读取用户输入、目标策划案、直接相关的 `AutoDoc/Design/`、`AutoDoc/Art/` 文档、它们直接引用的现有图片和目标媒体；不读取代码、配置、`AutoDoc/Program/` 或临时实现方案。
2. 按需求拆分意见创建或更新相应数量的策划案，每篇遵循年月日归档、英文文件名、状态对应的严格文件头、`P0/P1/P2` 优先级、六个必选章节、按用户要求追加的可选第七章和图片规则。`In Design`、`Todo` 与 `In Progress` 使用三行文件头；`Warning` 与 `Completed` 包含实现流程写入的 `plan:`、`review:` 追溯字段。
3. 每篇策划案至少包含一张能够解释玩法的实际图片；可以采用现有图、基于现有图编辑或新生成，最终文件统一进入对应 `AutoDoc/DesignPlan/media/` 目录。
4. 复核每篇只覆盖一个功能点或同模块强关联功能集合，没有跨模块杂糅、无关追加或多套无优先级路线。
5. 单独复核每篇 `### 6.1 验收方式`：只使用“流程log验收”“游戏内截图”“仅功能验收”，列明覆盖范围、场景和核心操作；用户未指定时默认流程log验收。
6. 单独复核每篇 `### 6.2 美术资产验收`：只包含美术资产齐备性和玩家可见品质要求，使用稳定 `ART-` 编号与独立通过条件；未选择游戏内截图时写明相关资产编排检视范围，选择截图时写明场景、目标状态和截图重点；不涉及美术资产时保留本节并写明范围依据，不创建占位编号。
7. 单独复核每篇 `### 6.3 程序功能验收`：只包含前置场景、玩家操作、预期结果和通过条件，使用稳定 `FUNC-` 编号；不涉及程序功能时保留本节并写明范围依据，不创建占位编号。
8. 复核第 6.2 节与第 6.3 节没有混表或重复通过条件，全部内容均不包含技术实现；跨小节需求分别建项并互相引用稳定编号。
9. 用户明确要求在策划案中记录实现方式建议时，只在可选的 `## 7. 实现方式建议` 中覆盖其指定或要求给出建议的范围；用户未要求时整章跳过，不主动调查、推断或补写实现内容。
10. 用户未指定优先级时，由主代理根据玩家价值、前置依赖、影响范围和验证紧迫度提出暂定建议并写明理由；不得无说明地默认某个级别。
11. 框架边界审计只检查文档职责、前六章无代码内容、可选第七章符合用户明确要求、统一归档和媒体流程，不读取代码判断实现可行性。

## 状态与定稿确认

这是用户明确要求的写作后确认门槛，必须暂停等待答复，不受普通检查清单“不自行引入逐步确认”的通用规则影响：

1. 新建策划案时将第二行写为 `state: In Design`。每次写作任务修改既有策划案（包括 `In Progress` 或 `Warning`）的正文、图片或其他文档内容时，也先改为 `In Design`，并移除仅供 `Warning`、`Completed` 状态追溯实现的 `plan:`、`review:` 行；只有执行用户已经确认的状态流转时不触发再次回退。
2. 本轮全部写作与自检完成后，向用户列出每篇文档的标题、路径、当前状态、优先级及建议理由，逐篇询问是否定稿。即使用户在写作前要求使用 Todo，也必须在展示本轮结果后再次确认。
3. 用户明确确认某篇定稿后，把该文档第二行改为 `state: Todo`，保留用户确认的第三行优先级，并复核 `Todo` 状态的严格三行文件头。不得依据主代理判断、文档完整度或用户未回应自行改为 Todo。
4. 用户未确认、明确不定稿或要求继续调整时，该文档保持 `In Design`。完成下一轮修改后重新展示结果并询问，上一轮确认不能自动沿用。
5. 多篇策划案可以一次向用户提问，但必须让用户能逐篇给出结论，只修改明确确认定稿的文档。
6. 策划案写作流程不得把状态改为 `In Progress`、`Warning` 或 `Completed`。只有实现策划案流程开始制定实施 Plan 时才能设置 `In Progress`；只有该流程在首次验收失败且完成两趟验收修正后主干仍失败时才能设置 `Warning`，主干验收通过并形成正式 Review 时才能设置 `Completed`。非主干验收项按类别如实记录，不单独阻塞完成。

## 结束审计

任务结束前在检查清单中对照前置“需求拆分说明与意见”，写明实际创建或更新的文档数量、路径、范围、优先级和用户逐篇定稿结论是否一致。若实际结果与建议篇数、边界或优先级不同，记录新的证据与偏离理由；不能静默把原计划拆开的内容合并，也不能遗漏已经确认需要独立成篇的功能。用户明确选择暂不定稿时，可以让对应文档以 `In Design` 结束，但报告必须记录该结论；尚未询问用户时不得提前完成结束审计。

随后按 `project-state-preflight` 主文件完成逐项复核、单次清理和独立报告；报告中必须重述需求拆分结论、最终文档清单和任何偏差。
